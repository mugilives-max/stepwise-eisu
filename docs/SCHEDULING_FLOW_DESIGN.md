# 日程の決め方の作り直し（設計）

作成: 2026-10-01（同日、言葉の整理と先生の回答を反映して改訂）。**段階0（請求の確定日）と段階1（締め切りと自動決定・言葉の置き換え）は 2026-10-01 に実装・本番反映**。段階2・3はまだ。実装で決めた細かいことは 12 章。規約の案は [TERMS_DRAFT_2026-10.md](TERMS_DRAFT_2026-10.md)。

## 1. なぜ作り直すか

今の流れは「先生が授業を案内 → 生徒が承認して確定」。実際には次のようになっている。

- 生徒は案内をほとんど確認しない。先生が代わりに確定することが多く、やり取りも LINE で済ませている。
- 生徒からすると、確定すると後で日時を変えにくい。そのため確定を遅らせる方が得になり、長い目で予定を立てにくい。直近の調整ばかりになり、確認の手間が増える。
- 日時を変えたいだけなのに「取消」「キャンセル」の操作を使うことになっていて、料金がかかる話と混ざって分かりにくい。
- 決まった曜日の授業を約束する形（いつもの枠）は取らない。先生はほぼ一人で回していて、予定は学期でも変わる。何より、継続した契約に近づくのを避けたい（規約案の第1条）。

## 2. 方針

1. **契約は1か月ごと。** その月の授業計画（回数・料金）は保護者の明示の承認が必要。ここは今と同じ。
2. **日程は先生がまとめて送り、締め切りまでに連絡がなければ決定する。** 生徒・保護者は、都合の悪い授業についてだけ連絡する。空き時間を入力する必要はない。
3. **先生が送ったものだけが進む。** 先生が予定表を送らなければ何も決定しない。送り忘れは管理画面で知らせる。
4. **前日23時までの日時の変更とお休みは無料。キャンセルは前日23時を過ぎてからのものだけ。** 言葉と料金を一致させる。
5. **LINE はそのまま使ってよい。** システムは会話の場ではなく、請求・授業記録・カレンダー・Meet の元になる台帳。LINE で決めたことを先生がシステムに入れる。
6. **今の仕組みを生かす。** 内部の状態（`offered` / `booked`）、先生の直接登録、取消の記録、キャンセル料、授業計画の行（`planLines`）、毎日0時10分の処理は、作り直さずに使う。変えるのは画面の言葉と操作の分け方。

## 3. 言葉

画面・メール・規約で同じ言葉を使う。内部の名前は変えない。

### 授業の状態

| 画面の言葉 | 意味 | 内部 | 今の画面の言葉 |
|---|---|---|---|
| 仮予定（◯/◯まで） | 先生が送った、まだ決定していない授業。かっこ内は締め切り | `offered` + `confirmBy` | 案内 |
| 決定 | 行うことが決まった授業 | `booked` | 確定 |
| 実施済み | 行った授業 | `booked` + `done` | 実施済 |
| お休み | 前日23時までの連絡で行わないことにした授業（無料） | 取消の記録（料金なし） | キャンセル済み |
| キャンセル | 前日23時を過ぎてから行わないことにした授業・連絡のない欠席（キャンセル料あり） | 取消の記録（料金あり） | キャンセル済み |

### 生徒・保護者の操作

授業ごとのボタンは **「変更・お休みの連絡」の1つだけ**。押すと、その時点で選べることだけが、料金と一緒に出る。

| いつ | 選べること | 料金 |
|---|---|---|
| 仮予定のあいだ | 日時の変更をお願いする（希望を一言） ／ お休みにする | なし |
| 決定後〜前日23時 | 日時の変更をお願いする（希望を一言） ／ お休みにする | なし |
| 前日23時〜開始前 | 開始を遅らせたい（先生に相談。応じるかは先生が決める） ／ キャンセルする | 遅らせても追加なし ／ キャンセル 1,000円 |
| 開始後 | ボタンは出さない（先生が欠席・遅刻を記録する） | — |

- 「日時の変更をお願いする」は依頼で、先生が日時を直すまで授業は元の日時のまま残る。
- 「お休みにする」は前日23時までなら連絡した時点で受け付ける（無料が確定）。先生は内容を見て処理する。
- 今の「この日時は難しい」（案内を消す）と「取消申請」は、この1つのボタンに置き換える。

### 先生の操作

| 画面の言葉 | 中身 | 今の言葉 |
|---|---|---|
| 予定表を送る | 作った仮予定をまとめて送る（通知は1回） | 案内（1件ずつ） |
| 直接決定 | 締め切りを置かずに決定する（授業が近いときなど） | 直接登録 |
| 日時を変更 | 仮予定・決定の日時を直す | 修正 |
| お休みにする | 前日23時までの連絡を受けて、行わないことにする（料金なし） | 欠席・キャンセルを登録 |
| キャンセルを記録 | 前日23時を過ぎた連絡・連絡のない欠席（キャンセル料の審査へ） | 欠席・キャンセルを登録 |
| 当日の開始時刻の変更 | 開始を遅らせたことを記録する（料金は変わらない） | （なし） |
| 予定を削除 | 入力ミスを消す（記録を残さない） | 予定を削除 |

## 4. 月の流れ

翌月分（例: 11月分）の流れ。日付は目安。

| 時期 | 先生 | 生徒・保護者 | システム |
|---|---|---|---|
| 1日〜2日 | 前月分の請求を生徒ごとに確かめる（請求ページ） | — | 3日の0時10分に前月分の請求を確定する |
| 〜15日ごろ | 翌月の授業計画の行と仮予定を作る。「先月と同じ並びで下書き」から直してもよい | — | — |
| 18日〜 | — | — | 翌月の予定表をまだ送っていない生徒を、管理画面のホームに「来月の予定がまだです」と出す（対象は今月に授業がある生徒） |
| 20日ごろ | 授業計画と予定表を送る | 保護者に授業計画の承認依頼、生徒・保護者に予定表が届く | 各仮予定に締め切り（`confirmBy`）を付ける |
| 〜25日 | 連絡のあった授業を LINE などで相談し、日時を変更するか、お休みにする | 都合の悪い授業だけ「変更・お休みの連絡」を使う。何もしなくてよい | 連絡は先生に知らせる |
| 26日 0:10 | — | 決定のお知らせ（1通）が届く | 締め切りを過ぎ、連絡のない仮予定を決定する。カレンダーの予定と Meet を作る |
| 翌月 | 授業・記録 | 決定後の変更・お休みは前日23時までに連絡する | — |

- 締め切りは「25日」と「送った日の3日後」の遅い方を既定にする（先生の回答で決定）。先生が送るときに変えてもよい。
- 授業計画の承認は、今の方針（2026-09-18「保護者の承認は授業を止めない」）のとおり、請求の可否だけを決める。承認がなくても日程は決定し、授業も実施できる。請求は承認されてから。管理画面では今と同じく「承認待ち」と出る。

## 5. 請求の確定日を3日に（2026-10-01 実装・本番反映）

先生の回答で、月の請求の自動確定を1日から3日に遅らせる。日程の作り直しとは独立した小さな変更なので、先に入れてよい。

- 今は `familyCloseMonths_` が毎日0時10分に動き、前月以前の締めていない月を確定する。そのため実際には毎月1日に確定する。
- **変更**: 今日が3日以降のときだけ、前月を確定の対象にする。前々月以前（保留が残った月）は今までどおり毎日やり直す。
- 確定日は `gas/FamilyBilling.gs` の定数 `BILLING_CLOSE_DAY_`（3）。保護者向けの説明文と食い違わないよう、設定画面からは変えない。
- 請求ページ（`#billing`）で、前月分が確定前の1日・2日は「3日の0時10分に確定します」と出す。生徒ごとの行から内容を確かめられる（今の画面のまま）。
- 規約案は第12条第2項。保護者向けの説明（保護者ページの「請求・お支払い」）も直す。

## 6. 画面

### 先生（管理画面）

- **生徒カルテの予定表**
  - 仮予定を作るとき、締め切りを入れる欄を出す（既定値は上のとおり）。
  - 何件かまとめて作ってから「予定表を送る」を押すと、通知が1回にまとまる。
  - 1件だけ送ることもできる。そのときも締め切りが付く。
- **授業の日が近い場合**
  - 締め切りが授業の前日23時より後になる仮予定は作らない。画面で「直接決定」を案内する（生徒には「授業を登録しました」が届く）。
- **「先月と同じ並びで下書き」**
  - 今月の決定した授業の曜日と時刻を、翌月の同じ週の並びに写した仮予定の下書きを作る。送るまで何も知らせない。
  - あくまで先生の手元の作業用で、生徒への約束にはならない。
- **ホーム**
  - 「日時の変更のお願い」と「お休みの連絡」を、やることとして出す。
  - 18日以降は「来月の予定がまだです」を出す。
- **授業の詳細**
  - 3章の先生の操作をボタンの名前どおりに並べる。
  - 前日23時を過ぎてから日時を直すときは「当日の開始時刻の変更」を選べる。記録だけで料金は変わらない。生徒ページに月ごとの回数を出し、たびたび続く生徒が分かるようにする。

### 生徒・保護者

- 予定表の仮予定には「◯/◯までに連絡がなければ決定します」と出す。
- 授業ごとのボタンは「変更・お休みの連絡」だけ（3章）。今の「この日時で確定」は残さない（何もしなければ決定するので不要）。
- 保護者のマイページ（子どもの予定表）にも同じボタンを出す（先生の回答で決定）。
- **「予定の共有」に1本化する（先生の回答で決定）**
  - 「授業希望（できる時間帯）」の入力はやめる。
  - 「授業不可（この日はできない）」と「共有予定（テスト・行事）」を、「予定の共有」1つにまとめる。
  - 種類は「テスト」「行事」「この日は授業ができない」から選ぶ。
  - 今までのデータは消さず、先生の画面では見られるようにする。

## 7. データ

D1 のマイグレーション `0019`（番号は実装時に確認）で `slots` に列を足す。台帳のシートの写しにも同じ列を足す（`ensureSchema_` の版を上げる）。

| 列 | 中身 |
|---|---|
| `confirmBy` | 仮予定の締め切り（`YYYY-MM-DD`、その日の23:59 JST まで）。空なら自動では決定しない（今ある案内はすべて空のまま） |
| `changeReqAt` | 「日時の変更をお願いする」を受け付けた時刻（ISO）。空ならお願いなし |
| `changeReqBy` | `student` / `parent` |
| `changeReqNote` | 希望の一言（500文字まで） |
| `sameDayShift` | 当日の開始時刻の変更として記録したら `1` |

- 変更のお願いが出ている仮予定は自動では決定しない。先生が日時を変更する・お休みにする・そのまま直接決定する、のどれかをしたら、お願いの列は空に戻す。
- 決定した授業への変更のお願いも同じ列を使う。日時を変更したら空に戻す。
- お休みとキャンセルは、今の取消の記録（取消ジャーナルとキャンセル料）を使う。前日23時までの受付はキャンセル料の対象にならない（今の判定のまま）。画面での呼び方だけを、料金の有無で分ける。
- 監査は既存の操作の記録（`addLog_`、取消ジャーナル）に残す。

## 8. サーバーの処理

- **仮予定**
  - `adminOffer_` と一括案内は `confirmBy` を受け取る。
  - 締め切りが授業の前日23時より後なら `errorCode: 'confirmByTooLate'` で断る。
  - 「予定表を送る」は、仮予定を保存したうえで通知を1通にまとめる。通知の ID は `schedule:<生徒>:<送信の要求ID>`。
- **変更・お休みの連絡**
  - 生徒は `lessonChange {k, slotId, choice, note, requestId}`、保護者は `familyLessonChange {ftoken, studentId, slotId, choice, note, requestId}`。
  - `choice` は `move`（日時の変更のお願い）／ `rest`（お休み）／ `late`（開始を遅らせたい）／ `cancel`（キャンセル）。
  - サーバーは受付時刻で、選べる `choice` を決める（3章の表）。期限を過ぎた `move` / `rest` は断り、画面を更新させる。
  - `rest` と `cancel` は今の取消申請の処理（受付時刻の保存、先生の審査、キャンセル料）に渡す。`move` と `late` は変更のお願いの列に書く。
  - 同じ要求 ID の再送は同じ結果を返す。お願いの取り下げも作る。
  - 先生へのメール【日時の変更のお願い】【お休みの連絡】を足し、設定で止められる種類に加える。今の【取消依頼】は前日23時を過ぎたキャンセルだけに使い、件名を【キャンセル】にする。
- **自動決定**
  - 毎日0時10分の `scheduled`（今は月次の請求確定だけ）に足す。請求確定とは別のフラグ（`SCHEDULE_AUTO_CONFIRM=1`）で入り切りする。
  - 対象: `status='offered'`、`confirmBy` が昨日以前、変更のお願いなし、授業日が今日以降、テストの生徒ではない。
  - 決定は先生の直接決定と同じ処理（カレンダー・Meet を含む）を、操作者 `system:auto` で行う。
  - 1件ずつ決定し、失敗した仮予定は残して翌日やり直す。すでに決定しているものは飛ばすので、二度決定しない。
  - 生徒ごとに決定した授業をまとめて、決定のお知らせを1通送る。
  - 授業日を過ぎた仮予定は決定しない（今の「期限切れの案内」として先生に出る）。
- **当日の開始時刻の変更**
  - `editBooked` に `sameDayShift: true` を足せるようにする。
  - 授業料の計算（`billingMonthCalc_`）は変えない。予定の分数のまま請求する。
- **授業計画の期間（段階3）**
  - `planLineSave_` で、通常の行の期間を暦の月の中に、追加・講習の行を2か月以内に絞る。
  - 規約の確認が終わってから入れる。

## 12. 段階1で実装したこと（2026-10-01）

- `gas/ScheduleFlow.gs`（列・締め切り・予定表の送信・変更のお願い・自動決定）。D1 `0019_schedule_flow.sql`、シートの `slots` 15〜19列目、`familyEmailPrefs.schedule`。
- 締め切りは授業ごとに「授業の2日前」を超えない（前日0時10分に決定し、前日23時まで無料で変えられるように）。それより近い授業（今日・明日）は締め切りなしで、今までどおり「承認待ち」から先生が直接決定する。案内そのものは断らない（管理画面の直接決定は案内を経由するため）。
- 「あとで送る」にした仮予定は `confirmBy='hold'`。生徒・保護者には見せず、生徒が自分で決定することもできない。生徒ページの「予定表を送る」で締め切りを付け、メールを1通送る。
- 自動決定はテストの生徒も対象（メール・カレンダーはテストの生徒では実際には出ない）。本番で【テスト】の生徒を使って確かめられるようにするため。
- 生徒・保護者の「お休みにする」は、仮予定なら案内の取り下げ（今の `decline`）、決定した授業なら今の取消の申請（`cancelReq`、前日23時までなので料金なし）。「キャンセルする」も `cancelReq`（期限後なのでキャンセル料の審査へ）。「日時の変更をお願いする」「開始を遅らせたい」だけが新しい操作 `lessonChange`。
- 締め切りのない（この仕組みより前の）案内は、今までの「授業登録」のカード（予定する・再調整）のまま出る。
- 管理画面のホームの「対応が必要な授業」の先頭に「日時の変更のお願い」。授業の詳細で日時を直す・直接決定するとお願いは済みになる。直さないときは「済みにする」。
- Worker の定期実行は `SCHEDULE_AUTO_CONFIRM=1` のときだけ自動決定を行う（`cf/wrangler.jsonc`）。止めるときはこれを外して公開し直す。
