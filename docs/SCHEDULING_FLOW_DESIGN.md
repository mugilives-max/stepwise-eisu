# 日程の決め方の作り直し（設計）

作成: 2026-10-01。**まだ実装していない**。規約の案は [TERMS_DRAFT_2026-10.md](TERMS_DRAFT_2026-10.md)。

## 1. なぜ作り直すか

今の流れは「先生が授業を案内 → 生徒が承認して確定」。実際には次のようになっている。

- 生徒は案内をほとんど確認しない。先生が代わりに確定することが多く、やり取りも LINE で済ませている。
- 生徒からすると、確定すると後で日時を変えにくい。そのため確定を遅らせる方が得になり、長い目で予定を立てにくい。直近の調整ばかりになり、確認の手間が増える。
- 一方で、決まった曜日の授業を約束する形（いつもの枠）は取らない。先生はほぼ一人で回していて、予定は学期でも変わる。何より、継続した契約に近づくのを避けたい（規約案の第1条）。

## 2. 方針

1. **契約は1か月ごと。** その月の授業計画（回数・料金）は保護者の明示の承認が必要。ここは今と同じ。
2. **日程は先生がまとめて送り、締め切りまでに申し出がなければ確定する。** 生徒・保護者は、都合の悪い授業についてだけ申し出る。空き時間を入力する必要はない。
3. **先生が送ったものだけが進む。** 先生が日程を送らなければ何も確定しない。送り忘れは管理画面で知らせる。
4. **確定後の日時の変更は、前日23時まで無料。** 変えやすくすれば、早く確定しても困らない。
5. **LINE はそのまま使ってよい。** システムは会話の場ではなく、請求・授業記録・カレンダー・Meet の元になる台帳。LINE で決めたことを先生がシステムに入れる。
6. **今の仕組みを生かす。** 案内（`offered`）・確定（`booked`）・先生の直接登録・取消申請・キャンセル料・授業計画の行（`planLines`）・毎日0時10分の処理は、作り直さずに使う。

## 3. 月の流れ

翌月分（例: 11月分）の流れ。日付は目安。

| 時期 | 先生 | 生徒・保護者 | システム |
|---|---|---|---|
| 〜15日ごろ | 翌月の授業計画の行と日程を作る。「先月と同じ並びで下書き」から直してもよい | — | — |
| 18日〜 | — | — | 翌月の日程をまだ送っていない生徒を、管理画面のホームに「来月の予定がまだです」と出す（対象は今月に授業がある生徒） |
| 20日ごろ | 授業計画と日程を送る | 保護者に授業計画の承認依頼、生徒・保護者に日程表が届く | 各案内に締め切り（`confirmBy`）を付ける |
| 〜25日 | 申し出のあった授業を LINE などで相談し、日時を直す（変更のメールが届く）か、取り下げる | 都合の悪い授業だけ「この日を変えてほしい」を押す（一言を添える）。何もしなくてよい | 申し出は先生に通知する |
| 26日 0:10 | — | 確定のお知らせ（1通）が届く | 締め切りを過ぎ、申し出のない案内を確定する。カレンダーの予定と Meet を作る |
| 翌月 | 授業・記録 | 確定後の変更は前日23時までに申し出る | — |

- 締め切りは「25日」と「送った日の3日後」の遅い方を既定にする。先生が送るときに変えてもよい。
- 授業計画の承認は、今の方針（2026-09-18「保護者の承認は授業を止めない」）のとおり、請求の可否だけを決める。承認がなくても日程は確定し、授業も実施できる。請求は承認されてから。管理画面では今と同じく「承認待ち」と出る。

## 4. 画面

### 先生（管理画面）

- **生徒カルテの予定表**
  - 案内を作るとき、締め切りを入れる欄を出す（既定値は上のとおり）。
  - 何件かまとめて作ってから「日程表を送る」を押すと、通知が1回にまとまる。
  - 1件だけの案内も、今までどおり送れる。そのときも締め切りが付く。
- **授業の日が近い場合**
  - 締め切りが授業の前日23時より後になる案内は作らない。画面で「直接登録」（今の先生の直接登録。生徒には「授業を登録しました」が届く）を案内する。
- **「先月と同じ並びで下書き」**
  - 今月の確定授業の曜日と時刻を、翌月の同じ週の並びに写した案内の下書きを作る。保存するまで何も送らない。
  - あくまで先生の手元の作業用で、生徒への約束にはならない。
- **ホーム**
  - 「この日を変えてほしい」が出ている案内と、確定後の変更の相談を、やることとして出す。
  - 18日以降は「来月の予定がまだです」を出す。
- **確定した授業の日時を直すとき**
  - 前日23時を過ぎてからの直しなら、修正の画面に「当日の時間変更（生徒の申し出）」を付けられるようにする。
  - これは記録のためで、料金は変わらない（規約案第4条）。
  - 生徒ページに月ごとの回数を出し、たびたび続く生徒が分かるようにする。

### 生徒・保護者

- **予定表の案内の行**
  - 「◯日まで（締め切り）に申し出がなければ確定します」と出す。
  - ボタンは「この日を変えてほしい」（一言・必須）と、今の「この日時で確定」（任意）。
  - 今の「この日時は難しい」は案内を消してしまうので、新しい流れの案内では出さない。
- **確定した授業**
  - 前日23時までは「日時を変えてほしい」を出す（一言・希望の日時を書ける）。
  - これは取消申請とは別の操作で、授業は消えず、先生が日時を直すまで元の日時のまま。
  - 前日23時を過ぎたら出さず、今の取消申請（キャンセル料の案内つき）だけを出す。
- **保護者も同じ操作をできるようにする**
  - 保護者のマイページ（子どもの予定表）にも同じボタンを出す。
- **「授業希望（できる時間帯）」の入力**
  - 新しい流れでは使わないので、目立たない場所へ下げる。消すかどうかは様子を見て決める。

## 5. データ

D1 のマイグレーション `0019`（番号は実装時に確認）で `slots` に列を足す。台帳のシートの写しにも同じ列を足す（`ensureSchema_` の版を上げる）。

| 列 | 中身 |
|---|---|
| `confirmBy` | 案内の締め切り（`YYYY-MM-DD`、その日の23:59 JST まで）。空なら自動では確定しない（今ある案内はすべて空のまま） |
| `changeReqAt` | 「変えてほしい」を受け付けた時刻（ISO）。空なら申し出なし |
| `changeReqBy` | `student` / `parent` |
| `changeReqNote` | 一言（500文字まで） |
| `sameDayShift` | 当日の時間変更として記録したら `1` |

- 申し出が出ている案内は自動では確定しない。先生が日時を直す・取り下げる・そのまま確定する（直接登録）のどれかをしたら、申し出の列は空に戻す。
- 確定した授業への「日時を変えてほしい」も同じ列を使う。日時を直したら空に戻す。
- 監査は既存の操作の記録（`addLog_`、取消ジャーナルと同じ考え方）に残す。

## 6. サーバーの処理

- **案内**
  - `adminOffer_` と一括案内は `confirmBy` を受け取る。
  - 締め切りが授業の前日23時より後なら `errorCode: 'confirmByTooLate'` で断る。
  - 「日程表を送る」は、案内を保存したうえで通知を1通にまとめる。通知の ID は `schedule:<生徒>:<送信の要求ID>`。
- **申し出**
  - 生徒は `changeRequest {k, slotId, note, requestId}`、保護者は `familyChangeRequest {ftoken, studentId, slotId, note, requestId}`。
  - 受け付けるのは、案内中の授業か、前日23時前の確定授業だけ。
  - 同じ要求 ID の再送は同じ結果を返す。
  - 先生へのメール【日程の変更希望】を足し、設定で止められる種類に加える。
  - 申し出の取り下げも作る。
- **自動確定**
  - 毎日0時10分の `scheduled`（今は月次の請求締めだけ）に足す。月次の締めとは別のフラグ（`SCHEDULE_AUTO_CONFIRM=1`）で入り切りする。
  - 対象: `status='offered'`、`confirmBy` が昨日以前、申し出なし、授業日が今日以降、テストの生徒ではない。
  - 確定は先生の直接登録と同じ処理（カレンダー・Meet を含む）を、操作者 `system:auto` で行う。
  - 1件ずつ確定し、失敗した案内は残して翌日やり直す。すでに確定している案内は飛ばすので、二度確定しない。
  - 生徒ごとに確定した授業をまとめて、確定のお知らせを1通送る。
  - 授業日を過ぎた案内は確定しない（今の「期限切れの案内」として先生に出る）。
- **当日の時間変更**
  - `editBooked` に `sameDayShift: true` を足せるようにする。
  - 授業料の計算（`billingMonthCalc_`）は変えない。予定の分数のまま請求する。
- **授業計画の期間（段階3）**
  - `planLineSave_` で、通常の行の期間を暦の月の中に、追加・講習の行を2か月以内に絞る。
  - 規約の確認が終わってから入れる。

## 7. 通知

[EMAIL_NOTIFICATIONS.md](EMAIL_NOTIFICATIONS.md) をあわせて直す。

| 相手 | 件名 | いつ | 設定 |
|---|---|---|---|
| 生徒 | 【ステップワイズ】◯月の予定表が届いています | 先生が日程表を送ったとき。日時の一覧と締め切り、「変更がなければ返事は不要です」 | 「授業の案内・登録」と共通 |
| 生徒 | 【ステップワイズ】◯月の予定が確定しました | 自動確定のあと、生徒ごとに1通 | 同上 |
| 保護者 | 保護者ページのお知らせ（本文1行目「◯月の予定表が届いています」「◯月の予定が確定しました」） | 同上。保護者あてのメールは本文に中身を書かない今の形を守る | 保護者の設定に「日程表・予定の確定」を足す |
| 先生 | 【日程の変更希望】（生徒名）さん | 生徒・保護者の申し出を受け付けたとき | 先生に届くメールの種類に足す |

日程表のメールは、案内ごとのメール（今の `offered`）の代わりに送る。まとめずに1件だけ送った案内は、今の `offered` に締め切りの1行を足して送る。

## 8. 段階

1. **段階1: 締め切りと自動確定**
   - 対象: `confirmBy`、日程表の送信、自動確定、確定のお知らせ、生徒・保護者の案内の行の表示、「この日を変えてほしい」。
   - 新しい案内から使う。今の案内は締め切りがないので、自動では確定しない。
2. **段階2: 確定後の変更**
   - 対象: 確定授業の「日時を変えてほしい」、当日の時間変更の記録、ホームのやること、送り忘れの知らせ、「先月と同じ並びで下書き」。
3. **段階3: 契約まわり**
   - 対象: 授業計画の期間の制限、規約の採用、保護者ページへの規約の表示。
   - 専門家の確認のあと。

各段階はテスト（`test/` に新しいファイル）、Worker と Apps Script の両方の公開、Pages の確認を行う。自動確定のテストは時計を締め切りの翌日に進めて確かめる。テストの生徒以外では確かめない。

## 9. 未決のこと（先生が決める）

1. 締め切りの既定値: 「25日」と「送った日の3日後」の遅い方、でよいか。
2. 「この日を変えてほしい」を保護者もできるようにするか（設計は「できる」）。
3. 確定のお知らせを保護者にも送るか（設計は「送る」）。
4. 確定後の「日時を変えてほしい」を、新しいボタンにするか、LINE だけで受けて先生が直す運用にするか（設計はボタンを作る。LINE で受けたときも先生が直せばよい）。
5. 「授業希望（できる時間帯）」の入力を残すか。
