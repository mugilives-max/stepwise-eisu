# 今後の実装計画

作成: 2026-09-07。現行コードとの照合は [REDESIGN_CURRENT_STATE.md](REDESIGN_CURRENT_STATE.md)。この計画は実装の順序を具体化する案であり、後続の全機能を一括で採用・公開するものではありません。

## 今回の到達点

保護者専用認証を実装し、授業記録を中心とした最初の機能を具体的な仕様と画面試作で確認できるようにします。利用中の保護者はいないため旧共通パスワード方式の互換運用は必要ない、という2026-09-07のユーザー指示を前提にします。

授業サイクルは「前回を確認 → 授業内容を記録 → 宿題へ反映 → 報告を下書き → 次回へ引き継ぐ」です。請求・実施済みの記録・通知は既存の明示操作を保ちます。

## 完成形の業務マップ

| 業務 | 現在あるもの | 初回の追加 | 後続候補 |
|---|---|---|---|
| 入塾・契約 | 生徒台帳、入塾日、状態、料金 | 保護者の初回設定 | 契約履歴、保護者と兄弟姉妹の対応 |
| 目標・月間計画 | 科目別回数・承認 | 既存機能を使用 | 学習目標、単元別計画、追加回数承認の強制 |
| 日程 | 案内、希望、NG日、取消依頼 | 対象授業への入口 | 予約枠と授業実体の分離、講師割当 |
| 授業 | 日時・科目・実施済み | 内容、理解状況、内部メモ | 到達度の評価、指導品質の確認 |
| 宿題・自習 | 登録・完了・削除 | 記録との対応、修正・取り下げ | 困りごとの申告、教材・提出物 |
| 評価・報告 | 成績・模試 | 報告下書き、次回準備 | 保護者公開、月次報告、閲覧履歴 |
| 請求・入金 | 実施集計、請求・入金登録 | 既存機能を使用 | 契約料金履歴と承認に基づく計算の一本化 |
| 休塾・退塾 | 生徒の停止、台帳状態 | 閲覧履歴を保持 | 契約終了、保護者のアクセス期限と保存方針 |

先生はカルテ・今日の授業から記録へ、生徒は既存ホームのやることへ、保護者は専用認証後の回数承認へ進みます。講師と管理者の役割は完成形では分けますが、初回は現在の先生1アカウントを使います。AIは読み取りツールを維持します。

## 段階と完了条件

| 段階 | 内容 | 完了の判定 |
|---|---|---|
| 0: 認証と照合（今回着手） | 保護者が自分で設定するパスワード、先生による設定コード発行、失敗制限、失効、対象生徒の分離。最新コードとの比較・初回仕様・試作 | ローカルの認証テスト成功。配布前にはテスト生徒で初回設定→ログイン→回数承認→再設定→旧セッション拒否を確認 |
| 1: 授業サイクル | 管理画面の授業記録、前回確認、宿題反映、次回準備、先生だけが見られる報告下書き | [初回仕様の受け入れ条件](LESSON_CYCLE_PHASE1_SPEC.md#7-受け入れ条件)を満たし、保存で請求・通知が変わらない |
| 2: 保護者へ報告を公開 | 先生が内容を確認して公開。公開版と編集中の版を区別。訂正・非公開への戻し方を設計 | 認証の実運用確認、他生徒・内部メモの非表示、公開操作の記録、下書きの混入なし |
| 3: 契約・料金・請求 | 月間回数の承認運用、料金の適用期間、過去料金の固定、請求二重登録の防止 | 過去の請求額が現在の単価変更で変わらず、承認と実施・請求の関係が説明できる |
| 4: 学習支援・複数講師・AI | 生徒側の学習振り返り、講師ごとの担当権限、読み取り支援、その後必要な更新系MCP | 実際の運用負担と効果を確認し、必要な機能から個別に着手 |

## 初回の範囲を絞る理由

予約と台帳を全面移行すると、Calendar・通知・請求への影響を同時に確認する必要が生じます。まず既存の授業IDに教師用記録を追加し、宿題は現在の `tasks` を使います。入力は「授業内容・取り組みの様子・次回の焦点」を中心とし、細かな採点項目やAIの自動判定を必須にしません。

報告下書きは定型文で作れます。AI接続は初回の依存条件にしません。保護者への公開は専用認証だけで完成するわけではなく、公開対象・公開版・取消の扱いまで段階2で整えます。

## 共通して先に整えること

- 本番反映前に2つのスプレッドシートのバックアップと現行GAS版を記録する。バックアップが取れているという推測で作業しない。
- 実データを使わないローカルテストを先行し、必要な本番確認は名前が `【テスト】` で始まる生徒だけで行う。メール・Calendarに触れる確認は別に扱う。
- 機能ごとにコミットを分け、HTMLとGASの対応版を記録する。単にGitへ保存した状態と、本番へ反映した状態を区別する。
- 記録追加時には古い画面からの上書き、宿題の二重追加、枠取消後の参照、書き込み途中失敗からの復旧を実装する。
- 生徒が見られる情報、保護者が見られる情報、先生だけの情報をAPIの返却項目でも分離する。

## 判断が必要になる時点

初回仕様と試作を見て、入力項目と「宿題を生徒へ反映」の操作を調整します。段階2では報告の公開先・公開頻度、段階3では過去月の承認と料金改定を決めます。これらが未決でも、現在の認証整備と教師用記録の実装準備は進められます。
