### 授業計画の科目に「種類」を持たせる（通常・演習・講習・英検対策など）と種類別の料金
- **背景**: 2026-09-11 に先生から提案。同じ英語でも通常・演習・講習・英検対策のように分け、それぞれにコマ数と授業料を設定したい。現状は `plans` が「生徒×月×科目→回数」の1行で、料金は月の合意（`billingAgreements`）の 30分単価×実施分数が科目によらず一律。授業（`slots`）は `subject` のみで種類を持たない。請求前の検査は「授業の科目が承認済み計画の科目にあり、回数以内か」を科目文字列で見ている。
- **方針案（2段階）**:
  1. 種類の導入: 種類の一覧は固定のマスタ（例: 通常・演習・講習・英検対策。先生が編集できる `lessonKinds` シートか Script Property）。`plans` に `kind` 列、`slots` に `kind` 列を追加し（既存行は「通常」扱い）、案内フォーム・案内編集・MCP の `offer_lessons` で種類を選ぶ。生徒ホームの「授業計画」は「英語（演習）3回」のように種類付きで表示。成績・授業の記録・宿題の期限（次の同じ科目）は科目単位のままにして種類は無視する。
  2. 種類別の料金: `plans` の行に単価（30分単価。コマの長さが種類ごとに一定なら1コマ単価と同じ）を持たせ、提案・承認の JSON にも含める。請求は授業ごとにその種類の単価で計算し、請求書・保護者画面に種類別の小計を出す。単価未設定の行は月の合意の単価に戻す。
- **決定（2026-09-11）**: ①固定の一覧（先生が設定ページで管理）、②種類ごとに標準の1コマの時間と料金を定め、長さが違う場合は時間あたりで按分、③種類は必須（既定は通常、既存分は通常扱い）、④保護者の承認画面・請求書に種類別の小計を出す、⑤第1段階→第2段階の順。
- **進捗**: 第1段階（種類のマスタ、計画・案内・MCP への種類、科目＋種類での請求前検査、表示）は 2026-09-11 に公開（GAS `2026-09-11-lesson-kinds`）。残りは第2段階: 標準時間・標準料金からの按分計算、提案・承認 JSON への単価、請求書・保護者画面の種類別小計、月の合意の 30分単価との関係整理。
- **影響範囲**: GAS（Code.gs の plans / slots 書き込み全箇所、BillingApproval.gs の提案・承認・請求、MCP の登録ツール）、管理画面の月間計画と案内フォーム、保護者ページの承認画面、生徒ホームの授業計画、テスト多数。第1段階で半日〜1日、第2段階でさらに半日程度の見込み。
- **関連**: `gas/Code.gs` planRows_ / billingPlanSet_、`gas/BillingApproval.gs` billingFee_ / billingPreview_ / billingApprovedPlan_、`kanri/index.html` LESSON_SUBJECTS、[MCP_DESIGN.md](MCP_DESIGN.md)
- **追加日**: 2026-09-11

### 授業情報を授業報告書のような画面に集約する

- **第一段階を公開済み（2026-09-09、v56）**: 既存記録に担当・単元・理解度・進度・宿題評価・テスト日・保護者への連絡を集約。月間計画/確定回数・次回授業・前回宿題の状況を同画面に表示し、生徒側は記録内から反映済み宿題の完了操作ができる。保存の再送・版管理・先生メモの非公開性を継承。仕様と確認結果は [SYSTEM.md](SYSTEM.md#local-lesson-workspace)。
- **既読を公開済み（2026-09-09、v56）**: 保護者が記録を開くと、その保護者アカウントの閲覧済み版を保存する。一覧では未読/既読/更新ありを表示。一覧表示・生徒の閲覧では既読にしない。料金の承諾とは別。確認印・確認ボタンは不要と確定し、実装対象から外す。
- **次の段階**: 保護者からの既存連絡を授業へ明示的に関連付けること、次回の予定単元との連携、運用後の表示調整。先生用の既読一覧は今回の対象外。日付・本文から連絡の対象授業を推測して結び付けない。
- **目的**: 予定・宿題・授業記録・連絡が散在している状態を改善する。授業報告書のように、1回の授業に関連する情報と前後のつながりを一目で把握し、必要な入力・確認も同じ画面で行えるようにする。
- **PDFとの関係**: 「A4のPDFにもできそうな、情報が整理されたレイアウト」が意図であり、PDFの生成・発行・ダウンロード機能は今回の対象ではない。1回の授業でA4相当の面積を埋める必要はなく、複数回分をまとめて見られる構成も可。1ページ2回などの固定配置は未決定。
- **集約する情報**: 授業日・科目・担当講師、月間予定回数のうち何回目か、予定単元と実際に扱った単元、理解度、予定に対する進度（進んでいる／遅れている）、テストまでの残り授業回数。前回の宿題の実施状況・正答率、次回授業日時・予定内容・次回までの日数、次回までの宿題と生徒が完了チェックできる欄も含める。
- **授業報告本文**: 長文を前提にせず、学習内容・教材や進め方・理解状況やつまずき・次回の対応を短い一段落（利用者の想定は3行程度）で記入する。例の内容は「植物の体のつくりと消化を学習し、基本事項の解説後に基本問題へ取り組んだ。全体的な理解は良好だが消化の用語の暗記が不十分だったため、次回以降に復習する」という程度。端末幅による折り返しを考慮し、3行固定で本文を切り捨てない。
- **連絡・確認**: 保護者への連絡欄、保護者からの連絡欄を整理する。確認印は不要。保護者側で既読かどうか分かれば十分という合意に基づき、上記の自動既読と表示を採用する。報告を開いたことと、月間料金等への承諾は別の状態として扱う。
- **既存機能との統合**: 予定・宿題・授業記録・連絡欄の正本を再利用し、転記や二重入力、別の独立した報告書データの乱立を避ける。自動表示できる日付・回数・次回予定等は既存データから表示し、理解度・実施内容・コメント等を追加入力する。先生・当該生徒・紐付いた保護者の閲覧範囲と先生用メモの非公開性を維持する。
- **実装時の整理点**: 月間の何回目かに数える授業の状態、科目別の次回授業・テストとの対応、予定変更後も保持する授業当時の情報、後から更新する宿題完了・連絡・確認状況を区別する。不明な予定や未確認の理解度・正答率を推測で補わない。
- **完了条件**: 授業前の確認→授業中の入力→授業後の共有→次回までの宿題・連絡確認を、関連ページを何度も探さず行える。既存情報の再入力が不要で、保存内容・公開範囲・予定との対応が整合している。細かな見た目は、この基本動作を実装した後で調整する。
- **関連**: [授業記録の仕様](LESSON_CYCLE_PHASE1_SPEC.md)、[現行の取消・成績票・連絡欄](SYSTEM.md#local-learning-services)、下記の授業画面・応答速度の課題。

- **目的**: 生徒・保護者の自然文から授業希望・授業不可時間等の登録を代行し、質問・使いづらさ・要望も蓄積する。連絡欄は受付・返信まで、自動登録は AI がツールで行い、定期ワークは稼働しない。
- **処理の条件**: サーバーに保存された本人・子ども・受付時刻を使う。日本時間で相対日付を解釈し、「夕方」など曖昧な日時は確認待ちにする。本文の名前やID、AIへの命令で権限を広げない。原文・解釈・登録結果を対応付ける。

- **登録制約**: 定員・授業不可・既存予定を保存時にも検証し、満員の希望は要調整。授業確定・保護者承認・実施・入金を推測で代行しない。利用者の要望は課題候補として扱い、仕様決定にはしない。
