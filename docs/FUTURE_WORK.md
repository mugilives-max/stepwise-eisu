| 項目 | 確認できた現状・課題 | 改善候補 |
|---|---|---|
| ① 対面授業のMeet | 現行コードは新規の対面授業にMeetを発行しない。過去に発行したリンクが残る場合がある。Meetが遅さの主因かは未計測。 | 対面ではMeetを表示しない案を検討。表示を隠すことと、既存Calendarの会議情報を削除することは別に判断する。 |

| ④ 個別ページの情報量 | 予定調整、授業記録、料金・成績、変更頻度の低い形式・連絡先・認証設定が同じページに集まっている。 | 普段の入口は予定・案内調整と直近の授業・宿題を中心にする。生徒設定を分け、家族設定もそこから開けるようにする。家族情報は兄弟共通で保持する。 |

- **設計・検証で保持する条件**: 授業記録は保存時公開、先生メモは非公開という現行条件を守り、準備の保存で誤公開しない。2人の入力を切替・再読込・保存失敗で混同／消失させず、未保存・保存中・公開済みを区別する。空き表示は予約保証にせず、実際の案内・確定時にもサーバーで定員を再確認する。高速化でも二重保存・定員超過・古い版への上書きの防止を維持し、通知を後処理にする場合は未送信・失敗・再送の扱いを設計する。
- **関連**: 現行構成・APIは [SYSTEM.md](SYSTEM.md)、記録と公開の条件は [授業サイクル仕様](LESSON_CYCLE_PHASE1_SPEC.md)。確認箇所は `gas/Scheduling.gs` のCalendar・定員処理、`gas/Code.gs` の `wish_` / `wishMany_` / `doPost` / `kanriStudent_`、`kanri/index.html` の `lessonEntry` / `load` と個別ページ。性能改善の一般的な根拠は [Googleの指針](https://developers.google.com/apps-script/guides/support/best-practices?hl=ja)。
