## 4. アカウントとデータの今の形

- **生徒が根っこ**。
  - 生徒（`students`）は専用リンクのコード（`code`）を持ち、そのコードを知っていることが本人の証明になっている。
  - このコードは、保護者が子どもの代わりに操作するとき、先生の直接決定、MCP などの内部処理にも使い回されている。
- **保護者アカウント＝グループ**。
  - `familyAccounts` 1件がメールとパスワード1組で、`familyLinks` で生徒とつながる。
  - 生徒を追加すると「◯◯さんのグループ」が自動で作られる。兄弟は1つのグループにまとめる。
  - 1人の生徒に、両親それぞれのログインを持たせることはできない。
- **請求は生徒ごと**。家族単位の締めは、あとから足した。
- **ログインの作りが4種類**。
  - 生徒：専用リンク
  - 保護者：PBKDF2・端末ごとのセッション
  - 講師：保護者と同じ作り
  - 先生：別の作り。SHA-256・端末1台・PIN への後戻りの経路あり
  - ほかに機械用の鍵が2つと、旧保護者方式の残りがある。
- **同じ情報があちこちに写されている**。
  - 名前は7か所
  - メールは4か所
  - 単価は4か所
  - 在籍状態は2か所
- **表は62**。そのうち旧方式の残りや移行用が約10ある（`parents`、`plans`、`planComments`、`monthAgreements`、`_importRuns` など）。

## 6. 不具合の疑い（確かめていない。直すかどうかは相談）

1. **MCP からの登録が、本番では【テスト】の生徒にしか効かない疑い**。書き込みの範囲を決める設定（`MCP_WRITE_SCOPE`）が Worker に渡っていない。
2. **成績票 PDF の保存・読み出しが失敗する疑い**。Worker 上では Drive を使えないため（`servicePdf`、PDF 付きの `serviceExamSave`）。いまは0件なので実害は出ていない。
3. **カレンダーの予定 ID や Meet の書き戻しが、別の書き込みで消える可能性**。後から反映された別の書き込みが表全体を書き直すため。前に Meet のリンクが出なかった件とは別の経路。
4. **生徒あてのメールが一度も届いていない**。受信確認済みの生徒が0人のため。「生徒にメールで知らせる」機能は、今は事実上動いていない。
5. **先生のパスワードの持ち方が弱い**。SHA-256 で、端末1台。初期 PIN `0000` への後戻りの経路が残っている。

## 7. 複雑さのおもな原因（まとめ）

1. **Apps Script のコードを、表計算をまねた D1 の上で動かしている**。そのため次のことが起きている。
   - 列を「何列目」で扱う書き方が残る。
   - 表の定義が3か所（D1・コードの列一覧・シートの見出し）にある。
   - 毎回の書き込みで表を丸ごと書き直す。
   - キャッシュや設定の代役が本物と違う動きをする。
2. **生徒を根っこにしたデータの形**。家族・請求・権限・ログインの組み立てが、すべて逆向きになっている。
3. **画面が大きな1ファイルずつ**。管理画面は約3,700行、生徒・保護者は約2,200行。使われていない部分が、見えないまま残っている。
4. **旧方式を残したまま新方式を足してきた**。保護者の認証、計画（月→行）、取消（申請→連絡）、案内（承認→締め切り）のそれぞれで、古い方が残っている。
