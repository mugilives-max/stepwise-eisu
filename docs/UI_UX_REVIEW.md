### 今回採用した運用方針（初回実装）

- 内訳は任意。講師が後から作成でき、下書き保存だけでは公開しない。公開版と編集中の版を分離する。
- 1授業につき主な内訳を1つ選ぶ。端数配分や複数内訳への重複加算はせず、副次的な内容はコメントへ。
- 実施済みの授業を基準に `1/2`・`2/2` を示す。過去の対応が足りなければ未確定。予定超過も表示するが修了・習得とはみなさない。
- 過去の報告は公開時の位置づけを保持し、明示的な訂正時だけ更新する。
- 承認回数の削減は自動で配分し直さない。部分配分・未配分を認め、超過は下書き保存まで。公開前に先生が見直す。
- 報告確認から公開と宿題反映をひと続きにする。内部は既存の別々の保存処理を使い、部分失敗を区別して再試行する。
- 入力は主項目に集中させ、PCでは計画欄を横、スマホでは下に置く。補足は折り畳み、データと非公開性は保持する。
- 宿題の縦幅に関する実画面の指摘を受け、「1件＝基本1行」に変更した。番号見出しを省き、基本の期限は一覧の上に一度表示。各行の「⋯」から期限変更・欄の削除を行い、個別期限だけ行の下に表示する。文字・タップ領域を縮小せず、重複表示を減らす。Enterでの追加と宿題ごとの完了管理は維持する（本番反映済み）。
- 先生用プレビューと保護者本人の既読を区別する。先生の表示確認では既読を付けず、その旨を画面に明示する。保護者本人が開いた版の既読は従来どおり保存する（合成家族セッション・D1・実ブラウザーで確認済み）。

実装の制約・API・受け入れテスト・残件は [仕様の正本](LESSON_CYCLE_PHASE1_SPEC.md#local-plan-outline) に集約する。以下の「試作」「実装前」の節は判断の経緯として残し、当時の未決事項を現在もすべて未着手と解釈しない。

### ローカルで追加した表示・操作

- 生徒ナビに「宿題」を追加し、`#tasks` / `#tasks?filter=open|done|all` で未完了・完了・すべてを切り替える。既定・不正なfilterは未完了。保護者は `#family/tasks` で同じ描画を共用し、選択した子どもの既存代理操作を維持する。
- ホームの予定表より前に、期限順の未完了を最大3件と件数を表示。「すべての宿題」「完了した宿題を見る・未完了に戻す」へ誘導する。完了履歴をホームに長く並べず、「自分で追加する」は残す。
- 一覧はサーバーが返した期限・時刻で並べ、期限不明は後へ置く。`S.today` に基づき「今日まで」「期限を過ぎています」を示し、端末時計から期限を再計算しない。「次回の同じ科目（予定未定）」と「期限なし」を区別する。
- 完了／未完了へ戻す操作は、安定した課題IDと目標の真偽値を既存 `taskDone` APIへ送る。保存中の多重操作を抑止し、エラー時は成功したふりをせず、同じ本文・目標状態で再試行できる。
- 宿題だけでなく持ち物・メモ、先生からの課題、自分で追加した課題を維持する。撤回済みは除外し、先生の課題を削除する操作は追加しない。自分の未完了項目の削除と既存の自己追加を残す。
- 追加欄の入力は画面・filterの往復で保持し、生徒の専用リンク／保護者セッションと子どもごとに分離する。子ども切替後に前の子どもの応答や再試行が新しい対象へ混ざらないよう確認する。先生用プレビューは表示のみで、完了・追加・削除を無効にする。

### 維持するデータ仕様と残る制限

| 対象 | 今回の扱い・根拠 |
|---|---|
| 期限 | `date / nextLesson / none` を保持。既存 `lessonTaskDueView_` が解決した値を表示し、予定変更・次回未定を画面で推測補完しない |
| 完了時の期限 | `lessonSetTaskDone_` の期限固定を維持。未完了へ戻すと既存サーバー処理で次回授業の期限を再解決する。元の課題ID・公開報告との対応は変更しない |
| 完了履歴 | 取得済み課題を画面で20件に切らず表示。ただし `studentState_` → `tasksFor_(id,45)` の範囲は据え置きで、全履歴ではない。条件は完了日時から45日ではなく期限日による絞り込みで、期限なし等は別扱いとなる |
| 保護者 | 同一の宿題一覧を共用し、既存家族トークン＋選択子どもの代理経路を使う。デモで保護者側を閲覧のみとした簡略化は本実装へ持ち込まない |
| 報告・請求 | 自己チェックの完了は理解度、添削、授業実施、保護者の既読・承認、料金発生とは別。報告公開や宿題反映の先生側処理は変更しない |

今後、過去の全完了履歴が必要なら期間指定・ページングを含むAPI設計を別途行う。今回の一覧化だけを理由に、既存取得範囲を全件取得へ広げたり、未取得の課題を0件と断定したりしない。

## 先生用ホームの目的と画面案（2026-09-22）

### 確認済みの目的

先生が挙げた主用途は **授業の確認・日程調整・授業記録の登録**。用途を別々の大きなカードに分けるより、対象の授業を確認した場所から必要な操作へ進める構成を検討する。

### 初回の配置案（未採用・比較用）

- 既存の共通カレンダーを維持し、初期選択日は今日とする。別枠の「今日の授業」を重複表示せず、「選択日の授業」に集約する案。
- PCではカレンダーと選択日の授業を横並び、スマホでは縦並びにする。各授業に日程調整と授業準備／記録登録／記録確認への入口を置く。
- 「実施済み」と「記録・宿題の共有済み」は別状態として示す。授業の実施だけで報告・宿題の共有が完了したとは扱わない。
- 過去の記録待ち、取消依頼、未入金は主作業の下にまとめ、対象へ直接進めるようにする。既存の他の要対応事項を削除する判断はしていない。
- 記録後に一覧へ戻るときは選択日を保持し、処理した授業の状態を更新する。

対話内に架空データだけの操作可能な画面案を作成した。日付選択、日程調整の入口、記録への移動、共有後の表示を試せるが、保存・送信・実データ更新はしない。入力画面は導線を説明するための抜粋で、実装済みの授業記録画面を置き換える新仕様ではない。

### 初回案へのフィードバックと再検討

先生から以下の指摘があった。移設の最終承認・実装指示とは区別する。

- 一度出した授業案内を直すために、いったん消して作り直した経験があり負担だった。対象の案内を直接修正できるようにしたい。
- 初回案の小さなカレンダーでは「どれだけ授業が入っているか」がぱっと分からない。先頭の時刻だけに省略する構成では情報が不足する。
- 現行の週間カレンダーは全く使っていない。ホームにある従来のカレンダーを「管理 > 授業」へ移し、週間カレンダーと置き換える案が挙がった。

現行コードの確認結果（2026-09-22）:

- `kanri/index.html` の `slotDelivery` / `slotEditHtml` には、確定前の案内を同じ授業枠のまま日時・時間・科目・種類・形式を修正する入口とフォームがある。
- 一方、`renderHomeDayCard` と `renderStudentDayCard` の案内行には「取り下げ」はあるが「案内を修正」がない。機能が一部の一覧にしか現れないことが、普段の操作経路で修正できない原因になり得る。過去の経験の原因がこれだったかは未確認。
- 確定後の授業は同じ日時編集の対象ではなく、未実施の場合の形式変更のみ。確定後の直接的な日時変更まで含むかは未確認。
- `renderLessons` は週間予定表が先頭で、共通の月間予定表は「月間予定表・選択日の詳細」の折り畳み内にある。こちらの月表示は未来の授業に絞っているため、単に開いて上へ移すだけではホームと同等の過去・実施済み表示にならない。
- 案内編集のローカル回帰テスト `test/scheduling-edit-offer.test.cjs` は36件通過。実データの編集・本番動作確認はしていない。

再提案の方向（2026-09-23にホーム・授業の役割分担を確認。配置の細部は実装プレビューで確認中）:

- **ホームは日々の作業**: 今日の授業、記録・共有の未完了、必要な対応を中心にする。「授業の予定表へ」から全体確認へ移動できる。
- **授業ページは全体把握と調整**: 従来の月間予定表を広く表示し、時刻・生徒・科目の一覧性を維持する。日ごとの件数は補助情報として検討する。案内中と確定済みを混同しない。
- **選択日の授業から直接編集**: 案内行に「修正」を置き、元の値を引き継いだ編集を開く。削除・新規作成を要求しない。保存後も表示月・選択日と一覧への戻り先を保持する。
- 週間予定表は主表示から外す方向で検討し、既存コードの削除や完全廃止は別判断とする。生徒・保護者の共通カレンダーは変更対象に含めない。

## 授業記録の目的と要件（2026-09-22の対話）

### 合意した目的と優先順位

1. **保護者への報告が第一**。個別指導の授業内容が保護者から見えにくくなることを防ぎ、「こんな授業をした」と伝える。先生の詳細な評価入力そのものを目的にしない。
2. **送信した授業計画との対応**。どの計画の何回目で、どういう位置付けの授業かを分かるようにする。先生のペース配分と、保護者が授業の必要性・追加が必要な理由を理解することにつなげる。
3. **次回までの宿題の登録・管理**。ノートのメモだけでは管理しづらい生徒を支援する。複数科目や課題量の増加により、残りの課題やペースを把握しづらくなることも課題として扱う。

先生が以前使っていた紙の記録には、理解度、宿題の実施・忘れ、正答率、テストまでの授業回数などがあった。しかし、PC・スマホで毎回細かく入力する負担が大きいため、すでに簡素化を進めてきた。項目が多いと視線が散り、どこに入力すべきか分かりにくいという本人の問題意識を、今回の設計の出発点とする。

### 合意した基本方針

- **主要な入力は「扱った範囲」と「コメント」の2つ**。範囲には単元だけでなく教材・ページ・問題番号も書ける方向とする。理解できたこと、つまずき、次回の対応は短いコメントで伝えられ、毎回別欄へ分けて入力することは前提にしない。
- **必要な情報と手入力する項目を区別する**。日時・科目・対象の計画・回数・次回予定など、既存データから分かるものは再入力させない。対象計画など未接続の情報は、正しい関連付けを設計してから表示する。
- **毎回書くものが自然に目に入る**。宿題・持ち物・連絡は必要に応じて使う。前回情報・準備・先生専用メモ・詳細評価が、保護者向け報告の主要入力と同じ強さで並び続けないようにする。
- **詳細項目を一律に廃止する決定ではない**。理解度・進度・正答率などの既存値は保持し、集計や講師間の引き継ぎに独立した項目が必要かを別途判断する。表示の整理とデータ削除を同一視しない。
- **同じ内容を二重入力しない**。報告と宿題管理には入力済みの情報を再利用する。今回の初回実装では確認後の公開・反映を一連化し、既存の別処理・再送・競合・完了状態の保護を維持する。
- **PC・スマホの両方で日常的に入力できること**を条件とする。文章を短く書ける設計にするが、固定の行数で本文を切り捨てたり、長文を必須にしたりしない。

### 情報の役割と扱い方

以下は基本方針に沿った情報整理。配置・折り畳みの試作は後述。今回採用した必須入力や保存・公開条件は仕様の正本に記載する。

| 情報 | 役割 | 扱い方の方向性 |
|---|---|---|
| 扱った範囲・コメント | 保護者が授業の内容と様子を理解する | 入力の主役。必要な説明を短くまとめる |
| 生徒・日時・科目 | 対象の授業を明確にする | 既存の予定・記録から自動表示 |
| 対象計画・内訳・何回目・残り・次回予定 | 全体の中での授業の位置を理解する | 計画全体の回数と内訳内の回数を区別。正しい関連付けから自動表示する方向 |
| 宿題・持ち物・連絡 | 次回までの行動を明確にする | 必要なときに入力。通常の期限は次回の同じ科目の授業を使う方向 |
| 前回の記録・宿題・準備 | 今回の指導を判断する | 参照情報として使い、転記させない |
| 先生用メモ・詳細評価 | 先生の補助、必要時の評価・引き継ぎ | 主入力を妨げない扱いを検討。非公開情報は分離 |

### 計画との対応で注意すること

- **回数上の位置と、学習上の位置付けは別**。「全何回のうち何回目か」は集計できても、「何のための授業か」「なぜ追加が必要か」は回数だけでは説明できない。計画の目的と今回の範囲・コメントを合わせて伝える方向で検討する。
- 初回調査の [lessonWorkspace_](../gas/LessonCycle.gs) は、同月・同科目の確定予定から順番を計算する。これは送信した計画への所属を表すものではなく、そのまま「この計画の何回目」と表示しない。
- [管理画面](../kanri/index.html) の `renderPlanUsage` は、期間・種類・追加案内を扱う計画の消化状況を別に表示している。既存の計画・割り当て処理と整合させる必要がある。
- 月をまたぐ計画、同科目の異なる種類、追加授業、送信済み・承認済みの区別、変更後の過去記録の扱いは未決事項。不明な対応を推測で確定しない。
- 追加が必要かは学習上の課題を踏まえた先生の判断と理由で伝える。残り回数だけで自動判定したり、料金承認・請求のルールを変更したりしない。

### 宿題管理で注意すること

- 先生側は宿題内容を一度入力し、報告と生徒の課題に再利用できることを目指す。期限の既定値と例外の変更は分かるようにする。
- 生徒側では、科目をまたいで「何が残っているか」「いつまでか」が分かることが重要。宿題を登録する画面と、生徒が実行を管理する画面は分けて設計する。
- 大きな課題の小分けや途中期限によるペース配分支援は**候補**であり、まだ実装範囲に含めない。先生が毎回細かい計画を入力する負担を増やさないことを条件に、別途必要性を確認する。

### 授業計画の内訳：任意の高度な設定

**合意した方向性**:

- 授業計画に「数と式・計算を2コマ、図形を3コマ」のような、学習内容と予定コマ数の内訳を持たせたい。コメントだけでは、毎回の授業との対応やペースを扱いにくい。
- **内訳は必須にしない**。通常の案内は内訳なしで作成・送信でき、授業の記録も続けられる。毎回すべての授業に詳細計画を立てる負担を増やさない。
- 案内作成時には「高度な設定」などの任意の入口に置き、夏期講習等で必要なときに使う。具体的な見出し・操作は未確定。
- 内訳なしで案内した後に、講師が指導・ペース管理のために内訳を追加できる方向とする。
- **内訳を作ることと保護者へ公開することは別**。講師専用で使う場合と、保護者に位置付けを伝えるために公開する場合を区別する。後から作った内訳を自動公開しない。
- 学習内容の内訳と、既存の回数・料金の案内／承認／請求は別の役割。内訳の作成・修正だけを理由に、承認済みの総回数や料金を変更しない。

**承認回数が減った場合**: 10→8コマ等では、先生が手動で再配分する。公開版が超過した場合は調整中とし、合計が現在の回数以下になってから再公開する初回仕様を採用した。下書きは保持し、自動比例縮小・削除はしない。部分配分と内訳未設定を認める。

### 内訳内の「何コマ目か」を表示する

- **先生の追加要望**: 「予定2コマ」だけでなく、今回が `1 / 2` なのか `2 / 2` なのかも分かること。単元ごとのペース配分を把握できるようにする。
- **試作に反映した表示**: `方程式の計算` の近くに `今回 1 / 2 コマ目`、補足に `予定2コマのうち1コマ目`。先生の入力画面と、内訳を公開する場合の保護者向け表示の両方に示す。
- 分母は**対応する内訳の予定コマ数**、分子は**その内訳の中で今回が何コマ目に当たるか**。講習全体の `全10回`、計画全体の何回目、実施済み総数とは混同しない。
- `2 / 2` は「その内容が身に付いた」「単元が完了した」という評価ではない。理解度・学習上の到達は授業コメント等で伝える。
- 手入力欄は増やさず、授業との関連付けから自動表示する方向。算出対象・並び順・過去の訂正時の扱いは未確定であり、単純に保存回数を足す実装にはしない。
- 内訳なし・今回の内訳未選択・何コマ目か未設定を区別し、根拠のない回数を埋めない。`3 / 2` のような予定超過は隠さず示す案とするが、それだけで追加承認・料金請求・学習上の追加必要性を確定しない。
- 計画内訳の表示名と、実際に「扱った範囲」の入力は別。内訳を選び直しただけで、入力した教材・ページ・コメントを上書きしない。

## 1. 評価の要点

使いづらさの主因は、利用者が「次に何をするか」「どこで操作するか」「どこまで済めば完了か」を、その都度判断する必要があることだと考える。

機能を活かしながら、一つの用事を始めてから終えるまでの、探し直し・判断のし直し・画面の往復を減らすことを改善の軸にする。

- 情報の優先順位: 対応が必要な項目より、月間カレンダーや通常の一覧が先に見える。
- 作業の連続性: 実施登録・授業記録・宿題反映が分かれ、参照したい前回情報も入力欄から遠い。
- 分類と導線: メニュー名から場所を予測しにくく、通知やボタンの移動先で対象を探し直す箇所がある。
- 状態の理解: 日時への返事と計画の承認、保存と公開と宿題反映の違いを利用者が読み解く必要がある。
- 端末への適応: スマホの月表示は文字が小さく、先生の週表示はPCでも横スクロールが発生する。

## 3. 課題と改善案

### UX-01: ホームで優先すべき行動が下に埋もれる

**現状**: 先生ホームは全体の予定表と予定の編集が先にあり、今日の授業・取消依頼・未入金などが後に続く。生徒ホームは予定表、予定の編集、やることリスト、授業登録、授業計画の順。やることリストは初期状態で開いているが、授業登録と授業計画は対応待ちがあっても閉じている。

**影響**: ページを開いても今すべきことが分かりにくい。スマホ幅の再現では、宿題見出しがページ上端から約1,000px、返事が必要な授業登録が約1,300pxの位置にあり、最初の画面では見えなかった。

**改善案**:

- ホーム上部に役割別の要点を置く。先生は今日の授業と要対応、生徒は次の授業と宿題・返事、保護者は承認・確認が必要なものを優先する。
- 要対応の件数と対象への入口は、折り畳みを開かなくても分かるようにする。
- カレンダーは全体の把握・日付選択に使う。上部の要点と同じ授業一覧を何度も繰り返さない。
- 対応済み・空の項目は小さくまとめ、要対応があるときだけ強く示す。

**確認条件**: 主要な端末幅で、今すべきことと開始ボタンが最初の画面から分かる。対応待ちを見つけるためにすべての折り畳みを開く必要がない。

**根拠**: [管理画面](../kanri/index.html) の `renderHome`、[ポータル](../assets/portal.js) の `renderHomePage`、`folds`、`renderOffers`、`renderMonthSummary`。

### UX-02: 授業後の処理が分かれ、完了条件が分かりにくい

**現状**: 実施登録、授業記録の保存・公開、宿題の「やること」への反映は別処理。宿題は記録を保存した後に「反映する内容を確認」→「宿題を生徒へ反映する」と進む。記録への掲載と、チェックできる課題への反映は別の状態になる。

**影響**: 先生が記録に宿題を書いて保存しても、課題への反映を忘れる可能性がある。「この授業の後処理は全部終わったか」を複数の場所で確かめる必要がある。

**改善案**:

- 一つの授業画面で「実施」「記録公開」「宿題反映」の状況と残作業を示す。
- 授業後の処理を一続きに進められる導線にする。候補は、記録保存後に次の必要操作をその場で示す方式、または確認内容をまとめた完了操作。
- 内部処理を一括化するかどうかは別途設計する。途中失敗時は完了した部分と未完了の部分を分けて示す。
- 完了済み宿題の保護、二重登録防止、訂正履歴、先生メモの非公開性を継承する。

**確認条件**: 一つの画面で後処理の完了を判断できる。再試行で宿題が重複せず、既に完了した宿題の状態が失われない。

**根拠**: [管理画面](../kanri/index.html) の `lessonHTML`、`renderLessonHomework`、[授業記録処理](../gas/LessonCycle.gs) の `lessonRecordSave` / `lessonHomeworkApply` 分岐。分離の理由は [既存の授業サイクル仕様](LESSON_CYCLE_PHASE1_SPEC.md) を参照。

### UX-03: 前回情報・準備と、今回の入力欄が離れている

**現状**: 当日以降の授業記録画面では、今回の入力、宿題反映、保護者への報告下書きの後に、前回の記録・未完了宿題・授業準備が続く。

**影響**: 「前回を確認→今日の内容を判断→今回を記録」という作業で上下の往復が起きやすい。再現画面では、PC幅でも前回確認はページ上端から約2,200pxの位置だった。

**改善案**:

- PCは前回の記録・宿題・準備の要点を入力欄の隣に置く。
- スマホは入力欄の直前に参照用の短い要点を置き、詳細を必要に応じて開く。
- 通常の授業後処理で使わない報告下書きや履歴操作は、主な入力を妨げない位置にまとめる。
- 授業日・生徒・科目と保存状態が、長い入力中でも分かるようにする。

**確認条件**: 前回の宿題・準備を参照しながら入力でき、大きな上下移動を繰り返さない。二人同時の授業記録でも対象を取り違えない。

**根拠**: [管理画面](../kanri/index.html) の `lessonHTML`、`renderPreparation`、`renderLessonPair`。

### UX-04: メニュー分類から機能の場所を予測しにくい

**現状**: 生徒の先生への連絡・成績票と振り返りは「設定」にある。保護者の請求・計画承認・連絡・通知設定は「保護者メニュー」にまとまる。先生の「月間計画・請求」では、計画作成・承認状況・消化状況の後に請求が置かれる。

**影響**: 「質問したい」「成績票を見たい」「入金を記録したい」という目的から入口を選びにくい。大きな分類の中で再び探す負担がある。

**改善案**:

- 予定、学習・授業記録、連絡、料金、設定という利用目的で整理する。
- タブを一律に増やすことは前提にしない。役割と利用頻度に合わせ、主ナビと画面内の入口を分ける。
- 先生の計画管理と請求処理には、それぞれ直接到着できる入口を設ける。
- 生徒・保護者の共通の予定表と代行操作は維持し、保護者向けの承認・料金への入口を分かりやすくする。

**確認条件**: メニュー名から連絡・成績票・請求の場所を予測できる。設定には主にアカウントや通知の設定が集まる。

**根拠**: [ポータル](../assets/portal.js) の `renderTabs`、`parentNavigation`、`renderFamily`、`render`、[管理画面](../kanri/index.html) の `renderStudent`、`renderPlanCard`、`renderBilling`。

### UX-05: 通知・ボタンから目的の対象へ直接到着しない

**現状**: 先生ホームの「請求・入金を確認」は `#s=生徒ID` を開くため、初期の「予定」タブへ移る。生徒のお知らせの授業記録リンクは `#history` を開き、対象の記録ではなく科目・種類別のフォルダ一覧から探し直す。

**影響**: ボタンに書かれた用事をそのまま開始できず、クリック後も探し直しが発生する。

**改善案**:

- リンクに生徒・対象月・授業・記録などの文脈を引き継ぐ。
- 通知から対象の記録や承認欄を開き、該当箇所が分かるようにする。
- 戻る操作でも直前の一覧条件や日付を保持する。
- 対象が更新・削除された場合は、理由と適切な一覧への入口を表示する。

**確認条件**: 「請求・入金を確認」で対象生徒の請求欄へ、授業記録の通知で対象記録へ進める。移動先でも閲覧権限を確認する。

**根拠**: [管理画面](../kanri/index.html) の `renderHome` 内の未入金リンクと `route`、[ポータル](../assets/portal.js) の `studentNoticeItems`、`renderHistoryPage`、`hashchange`。

### UX-06: 似た用語が異なる手続きに使われている

**現状**: 「案内」「承認」「確定」が授業日時への返事と、回数・料金を含む計画の承認で使われる。「授業登録」という見出しの主な内容は、先生から届いた日時への返事。

**影響**: 誰が何を承認するのか、日程の確定と計画承認がどう違うのか、操作前に判断する必要がある。

**改善案**:

- 表示名は「授業日時への返事」「回数・料金の確認」など、対象と行為が分かる短い言葉にする。
- 状態は「生徒の返事待ち」「保護者の確認待ち」のように次の担当者を示す。
- 本人が今操作できるものと、相手の返事を待つものを区別する。
- 見出し・ボタン・通知・完了メッセージの用語を揃える。

**確認条件**: 日時への返事と計画の承認を、説明文を読み比べなくても区別できる。短い「登録不可」など既に整理した表現を、必要なく長くしない。

**根拠**: [ポータル](../assets/portal.js) の `renderOffers`、`renderMonthSummary`、[管理画面](../kanri/index.html) の `renderPlanGroup`、`offerForm`。

### UX-07: カレンダーの情報量と表示幅が合っていない

**現状**: スマホ幅では月間カレンダー内の授業文字が9pxになる。先生の週間予定表は最小幅930pxだが、通常のページ枠は最大860px。PC幅の再現でも予定表の表示領域は約811pxで横スクロールが生じた。週表示は初期状態で7時から始まり、予定表内とページ全体で縦スクロールが分かれる。

**影響**: 読み取りにくく、夕方の授業や週末へ到達するまでの移動が増える。スマホでは日付選択と詳細の読み取りを一つの小さな枠で行う負担が大きい。

**改善案**:

- スマホでは日別の予定一覧を中心にし、月表示を全体把握・日付選択に使う。
- PCの週表示には十分な横幅を与え、実際によく使う時間帯を最初に表示する。時間外の予定へも到達できるようにする。
- 色に加えて短い状態名を示し、詳細では時刻・科目・対象者を読みやすく表示する。
- 小さい文字やボタンの密集を避け、スマホでのタップとPCでのキーボード操作を確認する。

**確認条件**: 月表示から選んだ日の詳細を無理なく読める。通常のPC幅で週全体を把握でき、初期位置から主な授業へ進みやすい。

**根拠**: [月表示CSS](../assets/calendar.css)、[週表示CSS](../assets/schedule-board.css)、[週表示描画](../assets/schedule-board.js)、[管理画面](../kanri/index.html) の `.wrap`。

### UX-08: 保存・公開・反映の意味と、入力内容の見え方が揃っていない

**現状**: 授業記録は保存時に公開、報告下書きと準備は保存しても非公開、宿題は記録への掲載と課題への反映が別。保存ボタン近くでは「取り組み・次回の焦点」を公開すると説明しているが、現在の生徒・保護者の記録本文には当該項目を表示していない。

**影響**: 書いた内容が誰に見えるのか、どの操作まで行えば相手に届くのか、確信を持ちにくい。

**改善案**:

- 入力欄を公開する内容と先生専用の内容に整理し、公開先を近くに示す。
- 保存後に「記録は公開済み・宿題は未反映」など、結果と残作業を具体的に表示する。
- 実際の公開画面と保存前の説明を一致させる。
- 「取り組み」「次回の焦点」は、公開画面に出すか先生用に整理するかを検討する。既存の入力項目の削除保留の判断は維持する。
- 標準期限が既に設定されている宿題で「＋期限を設定」とだけ示す箇所は、現在の期限と変更操作が分かる表現を検討する。

**確認条件**: 各項目の公開先、保存結果、宿題の反映状態を画面から判断できる。先生だけのメモや準備が生徒・保護者へ公開されない。

**根拠**: [管理画面](../kanri/index.html) の `lessonFields`、`lessonHTML`、[ポータル](../assets/portal.js) の `publishedRecordItem`。[既存の未決事項](FUTURE_WORK.md) の「授業記録の入力項目の整理」と併せて扱う。

### UX-09: エラーと再試行の示し方が機能によって異なる

**現状**: 授業記録等には入力保持・未完了表示・再試行がある一方、予定や宿題の一部の入力エラーは約2.8秒で消える画面下の通知で示す。

**影響**: 通知を見逃すと、どの入力を直すべきか、保存されたか、もう一度押してよいかが分かりにくい。

**改善案**:

- 入力エラーは該当欄の近くに残し、必要ならその欄へフォーカスを移す。
- 通信・保存失敗は操作箇所の近くに、入力保持の有無と再試行方法を示す。
- 保存中・完了・未完了の表現を揃える。短時間の通知は補助として使う。
- 保存結果が不明な場合は、既存の処理IDによる再試行など、重複を防ぐ方式を継承する。

**確認条件**: エラー表示を見逃しても修正箇所と未完了の作業を再確認できる。入力を失わず、二重送信が起きない。

**根拠**: [ポータル](../assets/portal.js) と [管理画面](../kanri/index.html) の `toast`、入力検証・保存処理、既存の授業記録・請求の再試行UI。

## 4. 配置と導線の方向性（候補）

| 利用者 | ホーム上部で分かること | 主な作業の流れ |
|---|---|---|
| 先生 | 今日の授業、返信・取消等の要対応、記録漏れ | 今日の授業 → 前回・準備を確認 → 記録 → 宿題反映・完了確認 |
| 生徒 | 次の授業、期限の近い宿題、日時への返事 | 宿題を確認・完了／案内に返事／予定表から授業可能日時を登録 |
| 保護者 | 確認・承認が必要な内容、子どもの直近の授業・記録 | 対象の計画・請求・記録を直接開く → 確認・承認・連絡 |

この表は主ナビの最終案ではない。生徒・保護者の共通カレンダーを維持しつつ、役割ごとの要点と専用操作の入口を調整する。兄弟まとめ予定表は既存の別課題として扱い、今回の整理から自動的に追加しない。

## 5. 改善の優先順位

**現在の優先順位**: 先生の指定により、授業記録を最優先とする。対象はUX-02・03・08・09と、上記の授業計画との対応。初回改修・保護者ログインの修正と本番家族経路の確認は完了。次はmirror確認と実運用での入力負担を評価する。その他の課題の着手順は未確定。

以下は初回調査での推奨順を判断の経緯として残したもの。ホーム優先を現在の合意として扱わない。

| 順番 | 対象 | 最初に具体化すること | 効果の確認 |
|---|---|---|---|
| 1 | UX-01・05 | ホームの優先順位、請求・通知から対象への直接移動 | 対応待ちを発見し、対象画面を開くまでの迷い・操作数 |
| 2 | UX-02・03 | 授業中の参照と入力、授業後の完了までの流れ | 記録と宿題反映に要する往復、反映忘れ、完了判断 |
| 3 | UX-04・06 | 機能の分類、ナビ・見出し・状態名 | 初見で連絡・成績票・請求の場所を見つけられるか |
| 4 | UX-07 | PCの週表示とスマホの日別表示 | 小さな文字、横・縦スクロール、対象日の選びやすさ |
| 5 | UX-08・09 | 公開先、保存状態、エラー・再試行の共通表現 | 誰に何が反映されたか、失敗後に何をすべきか分かるか |

順位は初回評価での推奨。UX-08・09の説明不一致や消えるエラーなど、小さく直せるものは各画面の改善と同時に扱える。開発工数と実業務での効果は未見積もり。

## 6. 維持する長所と既存の判断

- 単元とコメントを中心にした記録入力、次回の同じ科目を使う宿題期限、一括確定、先生からの表示専用プレビューは活かす。
- ホームの同じ予定の重複表示を増やさない。要点と詳細にはそれぞれ役割を持たせる。
- 授業可能日時は開始・終了時刻と任意メモで直接登録できる流れを維持する。
- 記録保存・宿題反映を分離した既存の理由を確認してから操作を統合する。画面上の一連化と、データ処理の一括化を同一視しない。
- 保護者の既読、計画への承認、授業日時の確定、請求・入金は、それぞれの意味を保持する。
- UI変更だけを理由にデータ項目の削除、公開範囲の拡大、請求条件・取消規則の変更を行わない。

## 7. 次の検討と確認方法

1. 授業記録を優先し、[実装済みの仕様と残件](LESSON_CYCLE_PHASE1_SPEC.md#local-plan-outline) から再開する。PC・スマホ両方の実際の入力負担を先生に確認する。
2. 公開判断後、D1・Worker・GASの参照経路・画面をまとめて反映し、合成データで本番の導線を確認する。ホーム等は別課題として扱う。
3. 次の代表的な用事を現行と改善案で比較する。

   - 先生: 今日の授業を開き、前回を確認し、記録と宿題を共有する。
   - 先生: 未入金の対象を開いて入金を記録する。
   - 生徒: 今日の宿題を確認し、完了にする。
   - 生徒: 授業日時に返事をし、授業可能日時を登録する。
   - 保護者: 対象の授業計画を承認し、新しい記録を読み、先生へ連絡する。

4. 所要時間、操作数、スクロールの往復、場所を探した回数、完了判断の迷いを記録する。現時点で改善率や秒数の達成値は設定しない。
5. 実装時は現在のコードと本番反映状況を再確認し、変更した画面・導線に絞って動作を検証する。進捗はFUTURE_WORK、確定した仕様は対応する既存文書へ反映する。

この文書の更新時点で、初回改修のデータ/API・画面実装、ローカル検証、本番移行・公開まで実施。本番の家族経路の最終確認・mirror確認・実利用での効果確認は残る。公開と受け入れ完了を混同せず、結果は仕様の正本とFUTURE_WORKへ反映する。
