# 作り直しの設計（目標の形）

作成: 2026-10-02。**案**。要件は [REQUIREMENTS.md](REQUIREMENTS.md)、今ある機能は [FEATURE_INVENTORY.md](FEATURE_INVENTORY.md)、日程の決め方は [SCHEDULING_FLOW_DESIGN.md](SCHEDULING_FLOW_DESIGN.md)。

この文書は「どういう形に作り直すか」と「どう切り替えるか」を決める。細かい画面の文言や API の一つひとつは、作る段階ごとに別に書く。

## 1. 方針

1. **家族が根っこ**。データ・権限・請求・ログインを、家族 → 生徒 の向きで組む。
2. **役割で権限を決める**。
   - スタッフは1つのアカウントに役割（講師・教室管理者・システム管理者）を組み合わせて持つ。
   - サーバーは操作ごとに、必要な役割と見てよい範囲を確かめる。
3. **D1 を本来の形で使う**。
   - 表は名前の付いた列と ID で持ち、行ごとに書く。表を丸ごと書き直さない。
   - 「何列目」で書く処理をなくす。
   - Apps Script のコードを D1 の上で動かす今の仕組み（表計算のまね）は使わない。
4. **Apps Script は外とのつなぎだけ**。メールの送信とカレンダー・Meet の作成だけを頼む。今と同じ「控え（`_effects`）→ 頼む → 結果を書き戻す」形。
5. **スプレッドシートは写しだけ**。台帳の正本は D1。人が見るための写しと、バックアップに使う。
6. **画面は役割ごとに分けて、小さな部品で作る**。1つの大きなファイルに詰め込まない。
7. **今の仕組みは作っている間も動かす**。新しい仕組みは別の場所で作り、そろったら切り替える（6章）。

## 2. 全体の形

```
スタッフの画面 (/staff/)  保護者の画面 (/family/)  生徒の画面 (/student/?k=)
        │                    │                     │
        └──────────── Cloudflare Worker（新しい API）────┘
                         │            │
                        D1        控え（_effects）→ Apps Script（メール・カレンダー・Meet・Drive）
                         │
              毎日: 写し（スプレッドシート）・自動処理（請求の確定・仮予定の決定）
              毎週: バックアップ
```

- **画面**：
  - 今と同じく GitHub Pages（www.stepwise-education.jp）に置く。
  - 組み立ての道具（ビルド）は使わず、ブラウザがそのまま読める小さなファイル（ES モジュール）に分ける。公開の手順は今と同じ「push するだけ」のまま。
  - 予定表などの共通の部品は、3つの画面で同じものを使う。
- **API**：
  - 今の Worker の中に、新しい入口（例: `/v2/...`）として作る。
  - 処理は領域ごとのファイルに分ける（予定・記録・計画・請求・成績・報酬・アカウント）。
  - 各処理は「ログインの確認 → 役割と範囲の確認 → 入力の確認 → D1 への書き込み（1つのまとまり）→ 控えに付随処理を積む」の順にそろえる。
- **同時に書いたときの扱い**：
  - 行ごとに版番号を持つ。
  - 画面が見ていた版と違えば「ほかの操作で変わりました」と返す。
  - 今の「台帳全体の版」はやめるので、カレンダーの書き戻しが消える心配もなくなる。
- **テスト**：
  - 今と同じ `node --test` と D1 の試験用の器（`test/helpers/d1-harness.cjs`）を使う。
  - 領域ごとにテストのファイルを持つ。

## 3. データの形

主な表だけを書く。すべての表に `createdAt`・`updatedAt`・`version`（版）を持たせる。お金に関わる変更は監査の記録（`auditLog`）にも残す。

### 3-1. 人とログイン

| 表 | 中身 |
|---|---|
| `families` | 家族（契約者）。表示名、メール、パスワード（PBKDF2）、状態（利用中・停止）、規約の同意、通知の設定 |
| `familySessions` | 保護者のログイン（端末ごと） |
| `students` | 生徒。`familyId`、姓名・ふりがな、学年・学校、専用リンクのコード、基本単価（計画の初期値）、授業の標準形式、在籍の状態（在籍・休会・退会）、生徒本人に許す操作 |
| `staff` | スタッフ。姓名、メール、パスワード（PBKDF2）、役割（講師・教室管理者・システム管理者の組み合わせ）、状態 |
| `staffSessions` | スタッフのログイン（端末ごと） |
| `staffRates` | 講師の時給の履歴（授業の時給・面談の時給・いつから）、源泉徴収をするかどうか |

- 1つの家族に生徒が何人いてもよい。生徒は必ず1つの家族に属する。
- 保護者のログインは家族に1つ（両親で共有）。
- 名前・メール・単価は、ここ1か所だけに持つ。今は名前が7か所、メールが4か所に写されている。

### 3-2. 予定

| 表 | 中身 |
|---|---|
| `lessons` | 授業。`studentId`、担当（`staffId`）、開始日時、分数、科目、種類、形式（対面・オンライン）、状態、締め切り、カレンダーの予定 ID、Meet の URL |
| `lessonRequests` | 生徒・保護者からの連絡。種類（日時の変更のお願い・お休み・開始を遅らせたい・キャンセル）、一言、受付時刻、誰から、処理の結果 |
| `cancellationFees` | キャンセル料の決定（規定額・減額・免除・理由）と、減額・免除の申請 |
| `sharedEvents` | 生徒・保護者が共有する予定（テスト・行事・授業ができない日） |
| `staffUnavailability` | 講師の休み（授業できない日時） |
| `meetings` | 面談。家族・生徒、担当、日時、分数、形式、Meet |

授業の状態（`lessons.status`）は次の6つ。

| 状態 | 意味 |
|---|---|
| `held` | 未送信。予定表にまとめていて、まだ送っていない |
| `proposed` | 仮予定（締め切りまで） |
| `decided` | 決定 |
| `done` | 実施済み |
| `rested` | お休み。前日23時まで、料金なし |
| `cancelled` | キャンセル。キャンセル料の対象 |

今のように行を消して取消を表すことはしない。授業の行は残し、状態で表す。

### 3-3. 授業記録

| 表 | 中身 |
|---|---|
| `lessonRecords` | 授業記録。`lessonId`、扱った範囲、コメント（公開）、講師用メモ（非公開）、計画の内訳のどこに当たるか、版。公開した版を残す |
| `homework` | 宿題。出した記録、内容、期限、状態（未完了・申告済み・確認済み・やり直し） |
| `handoverNotes` | 引き継ぎメモ。生徒、書いた人、宛先（次の担当・全員）、内容、既読 |

### 3-4. 計画・請求

| 表 | 中身 |
|---|---|
| `lessonKinds` | 授業の種類と、標準の時間・料金 |
| `plans` | 授業計画（生徒・期間）と、承認の状態 |
| `planLines` | 計画の行（科目・種類・回数・1回の時間・1回の料金） |
| `planUnits` | 計画の内訳（単元）。今の「計画の内訳」 |
| `approvals` | 保護者の承認・回数の調整・見送り。LINE・電話での承諾の記録を含む |
| `invoices` | 請求。**家族ごと・月ごと**。状態（確定待ち・確定・入金連絡あり・入金済み・取消） |
| `invoiceItems` | 請求の内訳（生徒ごとの授業・キャンセル料） |
| `payments` | 入金の記録 |

### 3-5. 成績・報酬・運用

| 表 | 中身 |
|---|---|
| `exams` | 試験（生徒、種類（定期テスト・模試）、名前、実施日、学年）と、全体の合計・順位・偏差値・判定 |
| `examScores` | 科目ごとの点数・満点・平均・順位・偏差値 |
| `examFiles` | 成績票の PDF・写真。誰が送ったか、取り込み済みか |
| `examReviews` | 振り返り（良かった点・課題・次の対策） |
| `payrollMonths` | 講師ごと・月ごとの報酬の明細（授業・面談の時間、時給、総額、源泉徴収、差引、状態：下書き・確定・支払済み） |
| `payrollItems` | 明細の行（授業・面談ごと） |
| `effects` | メール・カレンダーの控え（今の `_effects` を引き継ぐ） |
| `auditLog` | 誰がいつ何をしたか |
| `settings` | 設定 |

## 4. 権限

| 役割 | 見てよい範囲 | できること |
|---|---|---|
| 講師 | 自分が担当する授業と、その生徒（担当中か、直近3か月に担当した生徒）。成績は担当科目の詳細と、ほかの科目の合計だけ。料金・請求・判定・成績票は見ない | 記録・宿題・引き継ぎメモ・担当科目の成績の入力・自分の休みの登録・自分の支払明細 |
| 教室管理者 | 全部 | 運営のすべて |
| システム管理者 | 設定・アカウント・送信の状況 | スタッフのアカウント・役割・設定・送れなかった処理 |
| 保護者 | 自分の家族の生徒 | 承認・連絡・振込の連絡・生徒の操作の制限・成績票の写真を送る |
| 生徒 | 自分 | 連絡（保護者の制限による）・宿題・成績票の写真を送る |

確認はすべてサーバーで行う。画面でボタンを隠すのは、使いやすさのためだけ。

## 5. 画面

### スタッフ（/staff/）

役割に応じてメニューが変わる。

| 画面 | 中身 |
|---|---|
| 今日 | 今日と明日の授業、対応が必要なこと（連絡・記録待ち・決定前の仮予定・成績の取り込み待ち） |
| 予定 | 全体の月の予定表、仮予定を送る、予定表を送る、講師の休み |
| 生徒 | 家族ごとの一覧。生徒の画面は「予定・記録と宿題・成績・計画と料金・基本情報」 |
| 記録 | 授業記録と引き継ぎメモ |
| 計画 | 翌月の計画をまとめて作る（先月と同じ内容から） |
| 請求 | 月ごとの請求と入金 |
| 報酬 | 講師ごとの月の明細と確定（教室管理者）、自分の明細（講師） |
| 設定 | スタッフと役割、授業の種類、メール、送信の記録（システム管理者） |

### 保護者（/family/）

| 画面 | 中身 |
|---|---|
| ホーム | 兄弟の予定、要対応（承認・支払い） |
| 予定 | 予定表と「変更・お休みの連絡」 |
| 学習 | 授業記録・宿題・成績 |
| 計画と料金 | 承認・請求・振込の連絡 |
| 設定 | メール通知・生徒の操作の制限・規約 |

### 生徒（/student/?k=）

| 画面 | 中身 |
|---|---|
| ホーム | 次の授業、仮予定、宿題 |
| 予定 | 予定表と連絡、予定の共有 |
| 学習 | 授業記録・成績・成績票の写真を送る |

### ログイン

スタッフと保護者に、1つずつ分かりやすい流れを作る。

- メールとパスワードで入る。端末ごとにログインを保つ。
- 失敗が続いたらロックする。
- パスワードを忘れたらメールで再設定する。
- 初めての人は招待のメールから設定する。
- PIN はなくす。

## 6. 切り替えの進め方

### 案A（おすすめ）：横で作って、月初に一度で切り替える

- 新しい仕組みを別の入口で作る。画面は `/staff/`・`/family/`・`/student/`、API は `/v2/`。
- 作っている間、今の仕組みは不具合の修正だけにする。
- 全部そろったら、本番のデータの写しで移行を何度か試す。月初（請求の確定のあと）に、一度で切り替える。
- **一度で切り替えるのを勧める理由**：
  - データが少ない。生徒6人、授業68件、記録38件、計画17件。
  - 移行の手順を本番の写しで何度でも試せる。
  - 一方、少しずつ切り替えると、新旧の仕組みが同じデータを同時に書くための「つなぎ」が要る。家族が根っこの新しい形と、生徒が根っこの今の形の間では、そのつなぎが大きく複雑になる。
- **切り替えたあと**：
  - 今の画面は1か月ほど読むだけで残す。
  - 生徒の専用リンクのコードはそのまま引き継ぐ。
  - 保護者のパスワードも引き継げる。同じ方式なので、再登録は要らない見込み。

### 案B：領域ごとに少しずつ切り替える

- 例：成績や報酬のような新しい領域から作って使い始め、最後に予定・請求を移す。
- 早く使い始められる。そのかわり、新旧のつなぎを作る手間と、二重に動く期間の複雑さが増える。

### 作る順番（案A）

| 段 | 中身 | 確かめ方 |
|---|---|---|
| 1 | 土台：新しい API の骨組み、表、ログイン（スタッフ・保護者）、役割と範囲の確認、控え | テスト |
| 2 | 家族・生徒・スタッフの管理 | テスト・画面 |
| 3 | 予定（仮予定・決定・連絡・休み・共有・面談・カレンダーと Meet） | テスト生徒で実地 |
| 4 | 授業記録・宿題・引き継ぎメモ | 同上 |
| 5 | 計画・請求・キャンセル料 | 前月分の請求を新旧で比べる |
| 6 | 成績（新規） | テスト生徒 |
| 7 | 報酬（新規） | 前月の実績で計算してみる |
| 8 | 移行の道具と、本番の写しでの試験（2回以上）。保護者・生徒への案内文 | 新旧の件数と金額が合う |
| 9 | 切り替え（月初） | 1か月は旧画面を読むだけで残す |

移すデータは、家族・生徒・授業（過去を含む）・授業記録・宿題・計画・請求・入金・キャンセル料・講師・送信の控え。

移さないデータは、旧方式の表、成績（作り直しのため。了承済み）、作業の記録、ログ。ログは写しとバックアップに残す。

## 7. 決めること

1. 切り替えの進め方：案A（一度で切り替える）か、案B（少しずつ）か。
2. 作り直しの間は、今の仕組みは不具合の修正だけにしてよいか。
3. 画面の URL を `/staff/`・`/family/`・`/student/` に変えてよいか。今の `/kanri/`・`/hogosha/`・`/yoyaku/` からは新しい方へ案内する。
