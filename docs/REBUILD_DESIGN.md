# 作り直しの設計（目標の形）

作成: 2026-10-02。進め方は案A（横で作って月初に一度で切り替える）で決定（2026-10-02）。**1段目（土台とログイン）は本番に置いた**（8章）。要件は [REQUIREMENTS.md](REQUIREMENTS.md)、今ある機能は [FEATURE_INVENTORY.md](FEATURE_INVENTORY.md)、日程の決め方は [SCHEDULING_FLOW_DESIGN.md](SCHEDULING_FLOW_DESIGN.md)。

この文書は「どういう形に作り直すか」と「どう切り替えるか」を決める。細かい画面の文言や API の一つひとつは、作る段階ごとに別に書く。

## 1. 方針

1. **家族が根っこ**。データ・権限・請求・ログインを、家族 → 生徒 の向きで組む。
2. **役割で権限を決める**。
   - スタッフは1つのアカウントに役割（講師・教室管理者・システム管理者）を組み合わせて持つ。
   - サーバーは操作ごとに、必要な役割と見てよい範囲を確かめる。
3. **D1 を本来の形で使う**。
   - 表は名前の付いた列と ID で持ち、行ごとに書く。表を丸ごと書き直さない。
   - 「何列目」で書く処理をなくす。
   - Apps Script のコードを D1 の上で動かす今の仕組み（表計算のまね）は使わない。
4. **Apps Script は外とのつなぎだけ**。メールの送信とカレンダー・Meet の作成だけを頼む。今と同じ「控え（`_effects`）→ 頼む → 結果を書き戻す」形。
5. **スプレッドシートは写しだけ**。台帳の正本は D1。人が見るための写しと、バックアップに使う。
6. **画面は役割ごとに分けて、小さな部品で作る**。1つの大きなファイルに詰め込まない。
7. **今の仕組みは作っている間も動かす**。新しい仕組みは別の場所で作り、そろったら切り替える（6章）。

## 2. 全体の形

```
スタッフの画面 (/staff/)  保護者の画面 (/family/)  生徒の画面 (/student/?k=)
        │                    │                     │
        └──────────── Cloudflare Worker（新しい API）────┘
                         │            │
                        D1        控え（_effects）→ Apps Script（メール・カレンダー・Meet・Drive）
                         │
              毎日: 写し（スプレッドシート）・自動処理（請求の確定・仮予定の決定）
              毎週: バックアップ
```

- **画面**：
  - 今と同じく GitHub Pages（www.stepwise-education.jp）に置く。
  - 組み立ての道具（ビルド）は使わず、ブラウザがそのまま読める小さなファイル（ES モジュール）に分ける。公開の手順は今と同じ「push するだけ」のまま。
  - 予定表などの共通の部品は、3つの画面で同じものを使う。
- **API**：
  - 今の Worker の中に、新しい入口（例: `/v2/...`）として作る。
  - 処理は領域ごとのファイルに分ける（予定・記録・計画・請求・成績・報酬・アカウント）。
  - 各処理は「ログインの確認 → 役割と範囲の確認 → 入力の確認 → D1 への書き込み（1つのまとまり）→ 控えに付随処理を積む」の順にそろえる。
- **同時に書いたときの扱い**：
  - 行ごとに版番号を持つ。
  - 画面が見ていた版と違えば「ほかの操作で変わりました」と返す。
  - 今の「台帳全体の版」はやめるので、カレンダーの書き戻しが消える心配もなくなる。
- **テスト**：
  - 今と同じ `node --test` と D1 の試験用の器（`test/helpers/d1-harness.cjs`）を使う。
  - 領域ごとにテストのファイルを持つ。

## 3. データの形

主な表だけを書く。すべての表に `createdAt`・`updatedAt`・`version`（版）を持たせる。お金に関わる変更は監査の記録（`auditLog`）にも残す。

### 3-1. 人とログイン

| 表 | 中身 |
|---|---|
| `families` | 家族（契約者）。表示名、メール、パスワード（PBKDF2）、状態（利用中・停止）、規約の同意、通知の設定 |
| `familySessions` | 保護者のログイン（端末ごと） |
| `students` | 生徒。`familyId`、姓名・ふりがな、学年・学校、専用リンクのコード、基本単価（計画の初期値）、授業の標準形式、在籍の状態（在籍・休会・退会）、生徒本人に許す操作 |
| `staff` | スタッフ。姓名、メール、パスワード（PBKDF2）、役割（講師・教室管理者・システム管理者の組み合わせ）、状態 |
| `staffSessions` | スタッフのログイン（端末ごと） |
| `staffRates` | 講師の時給の履歴（授業の時給・面談の時給・いつから）、源泉徴収をするかどうか |

- 1つの家族に生徒が何人いてもよい。生徒は必ず1つの家族に属する。
- 保護者のログインは家族に1つ（両親で共有）。
- 名前・メール・単価は、ここ1か所だけに持つ。今は名前が7か所、メールが4か所に写されている。

### 3-2. 予定

| 表 | 中身 |
|---|---|
| `lessons` | 授業。`studentId`、担当（`staffId`）、開始日時、分数、科目、種類、形式（対面・オンライン）、状態、締め切り、カレンダーの予定 ID、Meet の URL |
| `lessonRequests` | 生徒・保護者からの連絡。種類（日時の変更のお願い・お休み・開始を遅らせたい・キャンセル）、一言、受付時刻、誰から、処理の結果 |
| `cancellationFees` | キャンセル料の決定（規定額・減額・免除・理由）と、減額・免除の申請 |
| `sharedEvents` | 生徒・保護者が共有する予定（テスト・行事・授業ができない日） |
| `staffUnavailability` | 講師の休み（授業できない日時） |
| `meetings` | 面談。家族・生徒、担当、日時、分数、形式、Meet |

授業の状態（`lessons.status`）は次の6つ。

| 状態 | 意味 |
|---|---|
| `held` | 未送信。予定表にまとめていて、まだ送っていない |
| `proposed` | 仮予定（締め切りまで） |
| `decided` | 決定 |
| `done` | 実施済み |
| `rested` | お休み。前日23時まで、料金なし |
| `cancelled` | キャンセル。キャンセル料の対象 |

今のように行を消して取消を表すことはしない。授業の行は残し、状態で表す。

### 3-3. 授業記録

| 表 | 中身 |
|---|---|
| `lessonRecords` | 授業記録。`lessonId`、扱った範囲、コメント（公開）、講師用メモ（非公開）、計画の内訳のどこに当たるか、版。公開した版を残す |
| `homework` | 宿題。出した記録、内容、期限、状態（未完了・申告済み・確認済み・やり直し） |
| `handoverNotes` | 引き継ぎメモ。生徒、書いた人、宛先（次の担当・全員）、内容、既読 |

### 3-4. 計画・請求

| 表 | 中身 |
|---|---|
| `lessonKinds` | 授業の種類と、標準の時間・料金 |
| `plans` | 授業計画（生徒・期間）と、承認の状態 |
| `planLines` | 計画の行（科目・種類・回数・1回の時間・1回の料金） |
| `planUnits` | 計画の内訳（単元）。今の「計画の内訳」 |
| `approvals` | 保護者の承認・回数の調整・見送り。LINE・電話での承諾の記録を含む |
| `invoices` | 請求。**家族ごと・月ごと**。状態（確定待ち・確定・入金連絡あり・入金済み・取消） |
| `invoiceItems` | 請求の内訳（生徒ごとの授業・キャンセル料） |
| `payments` | 入金の記録 |

### 3-5. 成績・報酬・運用

| 表 | 中身 |
|---|---|
| `exams` | 試験（生徒、種類（定期テスト・模試）、名前、実施日、学年）と、全体の合計・順位・偏差値・判定 |
| `examScores` | 科目ごとの点数・満点・平均・順位・偏差値 |
| `examFiles` | 成績票の PDF・写真。誰が送ったか、取り込み済みか |
| `examReviews` | 振り返り（良かった点・課題・次の対策） |
| `payrollMonths` | 講師ごと・月ごとの報酬の明細（授業・面談の時間、時給、総額、源泉徴収、差引、状態：下書き・確定・支払済み） |
| `payrollItems` | 明細の行（授業・面談ごと） |
| `effects` | メール・カレンダーの控え（今の `_effects` を引き継ぐ） |
| `auditLog` | 誰がいつ何をしたか |
| `settings` | 設定 |

## 4. 権限

| 役割 | 見てよい範囲 | できること |
|---|---|---|
| 講師 | 自分が担当する授業と、その生徒（担当中か、直近3か月に担当した生徒）。成績は担当科目の詳細と、ほかの科目の合計だけ。料金・請求・判定・成績票は見ない | 記録・宿題・引き継ぎメモ・担当科目の成績の入力・自分の休みの登録・自分の支払明細 |
| 教室管理者 | 全部 | 運営のすべて |
| システム管理者 | 設定・アカウント・送信の状況 | スタッフのアカウント・役割・設定・送れなかった処理 |
| 保護者 | 自分の家族の生徒 | 承認・連絡・振込の連絡・生徒の操作の制限・成績票の写真を送る |
| 生徒 | 自分 | 連絡（保護者の制限による）・宿題・成績票の写真を送る |

確認はすべてサーバーで行う。画面でボタンを隠すのは、使いやすさのためだけ。

| 画面 | 中身 |

### ログイン

スタッフと保護者に、1つずつ分かりやすい流れを作る。

- メールとパスワードで入る。端末ごとにログインを保つ。
- 失敗が続いたらロックする。
- パスワードを忘れたらメールで再設定する。
- 初めての人は招待のメールから設定する。
- PIN はなくす。

## 6. 切り替えの進め方

### 案A（おすすめ）：横で作って、月初に一度で切り替える

- 新しい仕組みを別の入口で作る。画面は `/staff/`・`/family/`・`/student/`、API は `/v2/`。
- 作っている間、今の仕組みは不具合の修正だけにする。
- 全部そろったら、本番のデータの写しで移行を何度か試す。月初（請求の確定のあと）に、一度で切り替える。
- **一度で切り替えるのを勧める理由**：
  - データが少ない。生徒6人、授業68件、記録38件、計画17件。
  - 移行の手順を本番の写しで何度でも試せる。
  - 一方、少しずつ切り替えると、新旧の仕組みが同じデータを同時に書くための「つなぎ」が要る。家族が根っこの新しい形と、生徒が根っこの今の形の間では、そのつなぎが大きく複雑になる。
- **切り替えたあと**：
  - 今の画面は1か月ほど読むだけで残す。
  - 生徒の専用リンクのコードはそのまま引き継ぐ。
  - 保護者のパスワードも引き継げる。同じ方式なので、再登録は要らない見込み。

### 案B：領域ごとに少しずつ切り替える

- 例：成績や報酬のような新しい領域から作って使い始め、最後に予定・請求を移す。
- 早く使い始められる。そのかわり、新旧のつなぎを作る手間と、二重に動く期間の複雑さが増える。

### 作る順番（案A）

| 段 | 中身 | 確かめ方 |
|---|---|---|
| 1 | 土台：新しい API の骨組み、表、ログイン（スタッフ・保護者）、役割と範囲の確認、控え | テスト |
| 2 | 家族・生徒・スタッフの管理 | テスト・画面 |
| 3 | 予定（仮予定・決定・連絡・休み・共有・面談・カレンダーと Meet） | テスト生徒で実地 |
| 4 | 授業記録・宿題・引き継ぎメモ | 同上 |
| 5 | 計画・請求・キャンセル料 | 前月分の請求を新旧で比べる |
| 6 | 成績（新規） | テスト生徒 |
| 7 | 報酬（新規） | 前月の実績で計算してみる |
| 8 | 移行の道具と、本番の写しでの試験（2回以上）。保護者・生徒への案内文 | 新旧の件数と金額が合う |
| 9 | 切り替え（月初） | 1か月は旧画面を読むだけで残す |

移すデータは、家族・生徒・授業（過去を含む）・授業記録・宿題・計画・請求・入金・キャンセル料・講師・送信の控え。

移さないデータは、旧方式の表、成績（作り直しのため。了承済み）、作業の記録、ログ。ログは写しとバックアップに残す。

## 8. 進み具合

### 1段目：土台とログイン（2026-10-02）

- **データベース**：今の台帳（`DB`、stepwise）とは別に `DB2`（stepwise-v2）を作った。表は `cf/migrations-v2/`。
  - `families`・`students`・`staff`・`staffRates`・`sessions`・`authChallenges`・`effects`・`auditLog`・`settings`
- **API**：今の Worker の `/v2/` に置いた（`cf/v2/`）。
  - 入口は `index.mjs`。共通の道具は `util.mjs`、ログインの作りは `accounts.mjs`、スタッフは `staff.mjs`、保護者は `family.mjs`、メールの控えは `effects.mjs`。
  - ログインのトークンは本文の `auth` に入れる。
- **ログイン**：スタッフと保護者で同じ作りにした。
  - パスワードは PBKDF2-SHA256・60万回。Worker の中で計算する（約1.3秒）ので、今の保護者のパスワードがそのまま使える。
  - 端末ごとにログインを保ち、30日使わなければ切れる。
  - 5回続けて間違えると15分ロックする。ない宛先と間違いは同じ答えにする。
  - 再設定はメールのリンク（30分）。招待はメールのリンク（7日）。どちらも1回だけ使える。
  - パスワードは12〜128文字。
- **最初の1人（代表）**：今の管理画面にログインしている端末で `/staff/` を開くと作れる。有効なシステム管理者がまだいないときだけ。パスワードは本人がその場で決める。
- **役割**：講師（teacher）・教室管理者（manager）・システム管理者（sysadmin）。スタッフの招待・役割・停止はシステム管理者だけができる。最後のシステム管理者は外せない。
- **画面**：`/staff/` を置いた（`staff/index.html`・`staff/app.js`・`assets/v2/`）。中身はログイン・最初の設定・招待・再設定・アカウント・スタッフの管理。保護者の画面は2段目。
- **テスト**：`test/v2-accounts.test.cjs`。
- **まだしていないこと**：メールの送り直しの画面。今の「送れなかった処理」は今の台帳だけを見ている。v2 のメールの失敗は `effects` 表に残る。

### 2段目：家族・生徒の管理と移行の準備（2026-10-02）

- **表**：`cf/migrations-v2/0002_people.sql`。
  - 家族に `guardianName`（保護者名）・`phone`・`note` を足した。
  - 家族・生徒に `legacyId`（今の台帳のどの行から写したか）を足した。
  - 生徒に `enrolledOn`（入塾日）・`subjects` を足した。
- **API**（`cf/v2/people.mjs`）：
  - 教室管理者：家族の一覧・登録・編集・停止、保護者ページの招待、生徒の登録・編集（在籍・休会・退会、基本単価、形式）、別の家族へ移す、専用リンクの作り直し。
  - 保護者：`family/students`（自分の家族の生徒。料金・先生用のメモ・専用リンクは出さない）。
  - 生徒：`student/me`（専用リンクの鍵で本人を確かめる。退会した生徒のリンクは使えない）。
- **切り替え前のメール**：設定 `live` が `'1'` になるまで、保護者あてのメールは実際には送らない。送らなかったことと理由を `effects` に残す。招待のリンクは画面に出すので、試すときはそれを使う。
- **移行の準備**（`cf/v2/migrate-identity.mjs`、システム管理者）：
  - 写す元は、今の `students`・`studentNames`・`生徒台帳`・`familyAccounts`・`familyLinks`・`familyProfiles`。
  - 「どう写るかを見る」は、書かずに結果と気になる点を返す。
  - 「写す」は、前に写した行（`legacyId` あり）を消して写し直す。
  - 保護者のパスワードと生徒の専用リンクは、そのまま写す。
  - 新しい仕組みで作った生徒が、写した家族に入っていたら止める。
- **画面**：`/staff/` に「家族と生徒」（教室管理者）と「移行」（システム管理者）を足した（`staff/families.js`・`staff/migrate.js`）。
- **テスト**：`test/v2-people.test.cjs`。土台は `test/helpers/v2-harness.cjs`。

### 3段目：予定（2026-10-02）

- **表**（`cf/migrations-v2/0003_schedule.sql`）
  - `lessonKinds`・`lessons`・`lessonRequests`・`sharedEvents`・`staffUnavailability`・`meetings`。
  - 授業は行を消さず、状態（未送信・仮予定・決定・実施済み・お休み・キャンセル）で表す。
- **API**（`cf/v2/schedule.mjs`）
  - **教室管理者**ができること：
    - 仮予定を作る（今すぐ送る／予定表にまとめる、くり返し）。締め切りは今と同じ決まり。
    - 予定表を送る、直接決定、日時などを直す（当日の開始時刻の変更の記録つき）。
    - お休み・キャンセル・実施済み・削除（入力ミス）。
    - 連絡を済みにする、講師の休み・共有予定・面談。
  - **講師**ができること：自分の担当の授業だけを見る、実施済みにする、自分の休みを登録する。
  - 同じ生徒・同じ講師の授業の重なりは断る。休みや「授業ができない日」に重なるときは、確かめてから登録する。
  - **保護者・生徒**：予定を見る（未送信は見せない）、変更・お休みの連絡、連絡の取り下げ、予定の共有。
    - お休み・キャンセルは、受け付けた時点で授業の状態を変える。キャンセル料は5段目で決める。
    - 保護者が生徒の操作を止めていれば、生徒はできない。
  - **毎日0時10分**（`runV2Scheduled`）：締め切りを過ぎた仮予定を決定する。
- **切り替え前の扱い**：カレンダー・Meet の作成と変更も、保護者へのメールと同じく実際には行わない（`effects` に held で残る）。
  - 切り替えたあとは、カレンダーの予定 ID と Meet の URL を授業・面談に書き戻す。
  - 切り替えのときは、新しい仕組みで決定してまだカレンダーにない授業（目印が `swv2` の授業）の予定を作る手順が要る（8段目）。
- **写し**（`cf/v2/migrate-schedule.mjs`、システム管理者）
  - 授業：slots から。担当は代表（今の講師がいればメールで当てる）。
  - 取消の申請と日時の変更のお願い：lessonRequests へ。
  - 共有予定・授業不可：sharedEvents へ。
  - 先生の休み：代表の休みとして写す。
  - 授業の種類も写す。授業希望は写さない。キャンセル済みの授業とキャンセル料は5段目で写す。
- **画面**
  - `/staff/` の「予定」（`staff/schedule.js`）：月の予定表、選んだ日の授業、連絡、仮予定を作る、休み、面談。
  - 新しく `/family/`（保護者）と `/student/`（生徒、`?k=`）を置いた。どちらも「準備中」と出す。予定の部品は `assets/v2/schedule-view.js` で共通。
- **テスト**：`test/v2-schedule.test.cjs`。

### 4段目：授業記録・宿題・引き継ぎメモ（2026-10-02）

- **表**（`cf/migrations-v2/0004_records.sql`）
  - 授業記録（`lessonRecords`）は1授業に1つ。宿題は `homework`、引き継ぎメモは `handoverNotes` と `handoverReads`。
- **API**（`cf/v2/records.mjs`）
  - **記録を書く画面**：授業・記録・宿題に加え、前回の記録・未完了の宿題・次の同じ科目の授業・テスト・引き継ぎメモ（未読を含む）を返す。
  - **下書き保存・保存して公開**
    - 生徒・保護者に見せるのは公開した版（`publishedJson`）だけ。直したあとは、もう一度公開するまで前の版が見える。
    - 公開すると、決定の授業は実施済みになる。
    - 講師用の欄（予定単元・理解度・進度・前回の宿題・正答率・次回やること・メモ）は公開しない。
  - **記録の無効化**：教室管理者だけ。理由が必須。
  - **記録待ち**：講師は自分の担当だけ。
  - **宿題**
    - 生徒・保護者が「できた」と報告し、確認の前なら取り消せる。
    - スタッフは確認するか、一言を添えてやり直しに戻す。
    - 「次の授業まで」の期限は、同じ科目の次の授業の日として出す。
  - **引き継ぎメモ**：書く・読んだ・しまう。宛先は特定の講師か、その生徒を担当する全員。
  - **講師が扱えるもの**：自分の担当の授業の記録と、担当の生徒の宿題・メモだけ。
- **写し**（`cf/v2/migrate-records.mjs`）
  - 授業記録は、最新の公開の版・先生だけのメモ・講師用の欄を合わせて写す。
  - 宿題（tasks）は状態をそのまま写す。授業準備のメモは引き継ぎメモにする。
- **画面**
  - `/staff/` に「記録」を足した（`staff/records.js`）：記録待ち・宿題の確認待ち・記録を書く画面。
    - 予定の授業から「記録」で開く。
    - 書きかけの内容は、ボタンを押して画面を描き直しても消えない。
  - `/family/` と `/student/` に「学習」を足した（`assets/v2/learning-view.js`）：公開した記録と宿題、「できた」。
  - スタッフの画面で名前を直せるようにした（最初の代表は仮に「代表」）。
- **テスト**：`test/v2-records.test.cjs`。
- **今の仕組みの不具合の修正**：保護者ページの請求の説明「翌月1日確定」を「翌月3日確定」に直した（`assets/lesson-report.js`）。

### 4段目の手直し（2026-10-02）

- **スタッフの名前**：姓（必須）と名に分けた（`cf/migrations-v2/0005_names_materials.sql`）。表示名は「姓 名」。
- **講師用の欄**（表記がずれないように選ぶ形にした。写した記録の自由な文字は、直すまでそのまま）
  - 理解度：5段階（5 よく分かっている 〜 1 まだ分かっていない）。
  - 予定に対する進度：予定単元を書いたときだけ出す（予定どおり・進んだ・遅れた）。予定単元が空なら保存しない。
  - 前回出した宿題をやってきたか：やってきた・一部だけ・やってこなかった・宿題なし。
  - 「次回の焦点」は「次回やること・気をつけること」と呼ぶ（次の授業・代講の講師への申し送り）。
- **扱った範囲の入力補助**：内容・教材・ページを入れて「範囲に足す」と、「不定詞 Keywork p.10〜12」の形で範囲の欄に足す。
  - 組み立てた内容は `lessonRecords.rangeParts`（JSON）にも残す。教材はこの生徒の記録と宿題から候補に出す。
- **写しの直し**
  - 授業の枠が消えて記録だけ残っていたもの（8月の1件。本格的に使い始める前の分）は写さない（本人の判断）。
  - 「全部を順に写し直す」（`admin/migrate/all/apply`）を足した。写した生徒につながる行を後ろの段から消し、家族・生徒 → 予定 → 授業記録の順に写す。切り替えたあとは使えない。
  - あとの段を写したあとで前の段だけを写し直そうとすると、「全部を順に写し直す」を使うように断る（外部キーで失敗しないように）。

### 5段目：授業計画・キャンセル料・請求（2026-10-02）

- **表**（`cf/migrations-v2/0006_billing.sql`）
  - `planLines`：1行 = 生徒 × 科目 × 種類 × 期間。**1回の授業料（fee）で持つ**（今は30分あたりで持つので1円ずれることがあった）。追加の計画は `parentId`。承認は行ごと（`approvedCount`・`approvedBy`・`approvedVia`・`consentDate`）。設計の `plans`・`approvals` は、行と監査の記録（`auditLog`）で足りるので作らない。
  - `cancellationFees`：キャンセル1つに1行。種類（開始前の連絡 1,000円／開始後・連絡なし＝その授業の授業料）、判断（判断待ち・規定どおり・減額・免除）、保護者の減額・免除の申請と回答。
  - `invoices`（家族ごと・月ごと、取消を除いて1つ）と `invoiceItems`（生徒ごとの授業・キャンセル料）。入金は請求の行に持つ（`payments` は作らない。分割の入金は今もない）。
  - `lessons.invoiceId`：請求に入った授業。取消で空に戻る。
- **計算**（`cf/v2/plan-calc.mjs`）
  - 授業（決定・実施済み）を承認済みの行に日付順で割り当てる（元の行 → 追加の行。回数まで）。請求済みの授業は請求したときの行のまま。
  - 授業の長さが計画の1回の時間と違うときは、時間で割り戻す。
- **API**（`cf/v2/billing.mjs`）
  - 計画：月の一覧・作る/直す（直すと承認は消えて下書き）・消す・下書きをまとめて家族にお知らせ（1通）・LINE などの承諾の記録（期間のあとの承諾はメモが必須）・先月と同じ内容で下書き・授業の種類と標準。
  - 同じ科目・種類の計画の期間は重ねない（回数を足すときは追加の計画）。請求に入った授業がある行は直せない・消せない。
  - 保護者：回数を選んで承認（0回は見送り。決まっている授業より少なくはできない）・先生が記録した承諾の確認か問い合わせ・振込の連絡・キャンセル料の減額や免除の申請（請求の確定前まで、1回）。
  - キャンセル：生徒・保護者の「キャンセル」と教室管理者のキャンセルで、判断待ちのキャンセル料ができる。取り下げで消える。
  - 請求：その月の末日までに実施済みで未請求の授業（前の月の承認待ちだった分も）と、判断済みのキャンセル料。
    - 確定できない：決定のまま実施済みにしていない授業・判断待ちのキャンセル料・減額や免除の回答待ち。
    - 計画の承認がない授業は請求しない。自動の確定は止め、手で確定すればその授業は次の請求に回る。
    - 取消（入金済みは不可）・入金の記録と戻し。
  - 毎日0時10分：**切り替えたあと**、3日以降に前月分を家族ごとに確定。止めた家族は3日に教室管理者へ知らせる。
- **写し**（`cf/v2/migrate-billing.mjs`）
  - 計画は30分あたりの単価から1回の授業料を計算して写す。
  - 今の仕組みでは行が消えているキャンセルの授業は、キャンセル料の控えから作る（お休みの控えはお休みの授業に）。
  - 請求は生徒ごとの行を家族ごと・月ごとにまとめる。振込の連絡も写す。取り消した請求は写さない。
  - 「請求を比べる」：写した請求の金額と、新しい計算の金額を家族ごとに並べる（この段の確かめ）。
  - 「全部を順に写し直す」に計画・請求を足した（4つ目）。
- **画面**：`/staff/` に「計画」「請求」（`staff/billing.js`、キャンセル料の判断は請求の画面）、`/family/` に「計画・お支払い」（`family/money.js`）、「移行」に4番目と「請求を比べる」。
- **テスト**：`test/v2-billing.test.cjs`。
- **直した不具合**：スタッフの画面で、予定の画面を開く前に、ほかの画面の data-id つきのボタン（記録の画面の「確認した」「読んだ」など）を押すと動かなかった（`staff/schedule.js` の `lessonById`）。
